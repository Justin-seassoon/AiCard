# 知识库技术架构对比 — aicard vs GovBot

> 目的：把 aicard 的知识库技术架构与 GovBot-PD-Outer（政务智能客服，见《项目分析说明.md》）做对比，明确各自优劣，找出 aicard 在「提高命中率」上的改进空间。
> 结论先行：**GovBot 的「多智能体 + 结构化槽位」体系不适合我们的轻量 FAQ 场景，不宜照搬；真正值得借鉴的是「hybrid 检索」和「embedding 选型」两个低成本高回报点。此外，我们发现一处自己代码的校验语义错位，可能直接误杀命中，建议优先修。**

---

## 1. 双方架构对比

| 维度 | aicard（SKB/VKB） | GovBot-PD-Outer |
|------|-------------------|------------------|
| **场景** | 日语「一问一答」FAQ（便利店/免税店/酒店） | 政务事项咨询 + 帮办（复杂多轮） |
| **知识组织** | Markdown 一问一答 → 主题=document、问答=chunk | 事项 Markdown（一事一文件）+ 问答 CSV + 槽位 JSON |
| **chunk 粒度** | 1 问答对 = 1 chunk（`Q+A` 整段） | 事项内容切片 + 事项名/实体分集合 |
| **embedding 模型** | Azure OpenAI text-embedding-3-small（1536 维，多语言通用） | bge-large-zh-v1.5（中文特化），5 种来源可切换 |
| **向量库** | pgvector（与业务库同库） | ChromaDB（独立服务） |
| **向量集合** | 单一（靠 domain 过滤 skb/vkb） | 4 个集合分而治之（事项名/问答/实体/内容切片） |
| **检索方式** | 纯向量余弦 topK=5 + 阈值 0.55 | 向量 + 意图识别 + 事项槽位收集（结构化匹配） |
| **query 处理** | 原始问题直接 embed，无改写 | query 改写 + 意图 + 槽位 |
| **生成** | LLM 受限生成（引用必须选自命中片段，唯一一次调用） | LLM 意图路由后回答（多次调用） |
| **防编造** | 非 LLM 校验（引用⊆命中 + 答案/片段相似度 0.6） | 无显式校验（靠槽位结构化保证） |
| **时延** | 检索毫秒级 + 1 次 LLM | 多次 LLM（意图+槽位+回答），时延高 |

---

## 2. 各自优劣

### 2.1 aicard 的优势（相对 GovBot）

1. **轻量、时延短**：单一 LLM 调用，检索走同库 pgvector 毫秒级，契合「<1.5s 端到端」的硬指标。
2. **防编造更强**：受控生成 + 非 LLM 校验，无依据明确回「暂无明确说明」，比 GovBot 依赖 LLM 本身更安全。
3. **架构简单**：pgvector 同库，免独立向量服务，运维成本低。
4. **多租户隔离**：customer/store/domain 三层过滤 + SKB/VKB 域隔离。

### 2.2 aicard 的劣势（命中率瓶颈）

1. **纯向量，无关键词/hybrid 检索**：日语专有名词短问（「朝食」「免税」「Wi-Fi」「チェックアウト」）纯向量可能漏检或相似度偏低。
2. **embedding 非日语特化**：text-embedding-3-small 是多语言通用模型，对日语的检索精度未必最优。
3. **无 query 改写 / 同义扩展**：近义问法（「お会計のとき何を確認」vs「お会計のとき必ず確認」）向量易串扰。
4. **校验段 embedding 语义错位（疑似 bug，见 §3.1）**：可能误杀本应命中的答案。

### 2.3 GovBot 的优势（可借鉴点）

1. **结构化槽位收集**：意图 + 槽位（业务场景/动作/主体/约束）做结构化匹配，不纯靠向量，精度高。
2. **中文特化 embedding**：bge-large-zh-v1.5 对中文检索优化，命中率优于通用模型。
3. **query 改写**：改写后的问题再检索，提升召回。
4. **多集合分治**：事项名检索 vs 内容切片检索分离，各司其职。

### 2.4 GovBot 的劣势（不适合我们的场景）

1. **重**：多智能体（LangGraph 图）+ 多次 LLM 调用，时延高、复杂度高。
2. **无显式防编造校验**：靠槽位结构化约束，一旦槽位没收集到，容易乱答。
3. **面向复杂政务流程**：其槽位体系针对「事项帮办」设计，我们的「一问一答 FAQ」没有对应需求，照搬是过度设计。

## 3. 提高命中率的改进空间（分优先级）

### 3.1 P0 —— 自己代码的校验语义错位（疑似 bug，建议优先修）

**现状**（`SkbService.answer` + `KnowledgeSeeder.seed`）：

- 检索段：`embeddings.embed(question)` 生成问题向量，与 `chunk.embedding`（也是**问题**向量）比对 —— ✅ 语义一致。
- 校验段：`maxSimilarity(answer, cited)` 里 `embeddings.embed(c.text())`，而 `c.text()` 是 `"Q: 问题 A: 答案"` **整段** —— ⚠️ 用「答案」向量和「问题+答案」全文向量做余弦。

**影响**：答案向量 vs 问答全文向量语义错位，相似度系统性偏低；θ_check=0.6 可能把本应命中的答案误判成 `no_match`，直接拉低命中率。

**改法**：把 chunk 拆成 `question_text` / `answer_text` 两字段（或额外存 `answer` 的向量），检索用 question 向量，校验用 answer 向量。需要一次 schema 迁移（V7）。

### 3.2 P0 —— 加关键词/hybrid 检索兜底

**现状**：纯向量，无关键词匹配。

**改法**：对高频专有名词（朝食/免税/税/ATM/Wi-Fi/チェックアウト/大浴場/駐車場…）建关键词索引或精确匹配，向量检索 miss 或相似度低时兜底。这是提升专有名词短问命中率最直接的手段，成本低、见效快。

### 3.3 P1 —— 评估日语 embedding 模型

**现状**：text-embedding-3-small（多语言通用）。

**改法**：用 `KnowledgeEvalRunner` 实测当前模型在日语 QA 上的命中率基线，再对比 `text-embedding-3-large`、`multilingual-e5-large` 等，择优选。这是「治本」，但需要实测数据支撑，且换模型要重新灌库。

### 3.4 P1 —— query 同义扩展 / 改写

- **规则层同义扩展（零成本）**：免税→tax free→免税手続き、チェックアウト→レイトチェックアウト 等，检索前做同义词归一。
- **LLM 改写（增时延）**：改写后的问题再检索，但增加一次 LLM 调用，与 <1.5s 时延目标冲突，1.0 不建议。

### 3.5 P2 —— 知识内容治理（非架构，但直接决定命中率）

验收评估文档已列，是内容命中率最直接的来源，但不是架构问题：

- **近义问法去重**：如「お会計のとき何を確認しますか」两条答案互相串扰（评估报告 P1-3）。
- **补遗漏场景**：外貨両替 / Wi-Fi 案内 / 接客基本用语 / セルフレジ年齢確認。
- **术语统一**：品牌术语（マルチコピー機 而非 マルチメディア端末）、敬语一致。

## 4. 建议

| 优先级 | 项 | 类型 | 成本 | 预期收益 |
|--------|----|------|------|----------|
| **P0** | 修校验段 embedding 语义错位 | 自己的 bug | 低（V7 迁移 + 小改） | 直接减少误杀，提命中率 |
| **P0** | 关键词/hybrid 检索兜底 | 借鉴 GovBot 思路 | 低 | 专有名词短问命中率显著提升 |
| **P1** | 日语 embedding 选型实测 | 借鉴 GovBot「特化模型」 | 中（需实测+重灌库） | 治本，整体检索精度提升 |
| **P1** | query 同义扩展 | 借鉴 GovBot「query 改写」 | 低（规则层） | 近义问法召回提升 |
| **P2** | 知识内容治理 | 非架构 | 低（内容编辑） | 内容层面命中率最直接来源 |
| ❌ 不做 | 多智能体 + 结构化槽位 | 照搬 GovBot | 高 | 不适合 FAQ 场景，过度设计 |

**一句话**：GovBot 的「结构化槽位 + 多智能体」是复杂政务场景的重武器，我们的轻量 FAQ 用不上；它身上真正值得拿的是「关键词兜底 + 特化 embedding + query 改写」这几个轻量手法。而比借鉴更重要的是——**先修掉我们自己校验段的语义错位**，那可能是当前命中率的最大隐性杀手。
