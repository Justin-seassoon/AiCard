# 两腿 demo · 范围界定

> 日期：2026-10-16（v2：依范围调整重写）
> 用途：**界定本轮 demo 的开发范围**（做什么 / **明确不做什么**），供开发（含 AI agents）照此执行
> 关联：`docs/baseline/2026-10-16-产品需求文档-唯一基线.md`、`docs/baseline/2026-10-16-两条腿-技术需求文档.md`
> 分工前提：**真机联调由硬件团队主导**；**客户触达由商务团队推进**；全职硬件负责人**已有**

---

## 0. 一句话

本轮把**两条腿做到「完整可用」**：
- **腿 A**：软件**可迭代**（协议/OTA 已真机调通，联调=硬件功能完善，云端工作量小，不受影响）；
- **腿 B**：**①②③ 三项全做**，**仅排除「用户/登录/鉴权」与「多租户硬化」**。

目的：真机稳定演示 + 完整 B 腿演示 → **让投资人/客户相信我们更专业** + 撬动真实对话。

---

## 1. 范围原则

1. **完整**：①③② 都要端到端可用（不做半成品）；仅 §3.2 两项除外。
2. **顺序即优先级**：**① → ③ → ②**（按「零件齐备度」）。时间紧时，**② 先让位**——它最重、demo 价值最弱，不应拖累 ①③ 的完成度。
3. **每项有「完成标准」**（§4）——达标才算做完，避免「看起来做了」。
4. **人工审核是硬门**（① 的候选**绝不自动入库**）。

---

## 2. 腿 A · 可迭代 + 配合联调

腿 A **软件不再冻结**——因**协议、OTA 等已真机调试过**，联调只是硬件功能完善，**云端几乎无额外工作量**，故可并行做功能迭代。

| 类别 | 内容 |
|---|---|
| **配合联调** | 待冻结参数 9 项（等 ODM 反馈定稿）、VKB 真机链路（依赖端侧 `button_event(ok)`）、耳机输出路由 |
| **功能迭代** | 按需（具体项另行登记）。**不影响联调**——协议/OTA 已冻结且真机验证过 |

> 腿 A 的 demo 成功标准：真机上核心场景**稳定**演示（连续对话翻译 / SKB 问答 / VKB 撞库确认 / 广播）。

---

## 3. 腿 B · ①②③ 全做

### 3.1 做什么

**① 自生长知识**（端到端闭环）
```
qa_log(status=no_match) → 缺口池聚合 → LLM 起草候选(带出处)
  → 后台审核(通过/编辑/驳回) → 入库(document.status: draft → published)
```
落点：迁移 **V18** `knowledge_gap` + 新模块 `skb/curation/` + 后台审核页；复用 `qa_log` / `KnowledgeStore` / `LLMProvider`。

**③ 文档/文书处理**
- `report/` **输出端升级**为文件生成（xlsx / docx），先覆盖 1 类社内文书；
- 前置 **C4**（报表聚合从「按设备」泛化到「按租户/用户」）。
- ⚠️ 优先走**结构化抽取 + 模板填充**（POI），**不引入代码沙箱**（重资产、Java 单体异构）。

**② agent 执行**
- 新增 `agent/`：任务状态机（持久化）+ 工具注册表 + `plan→act→observe→reflect`；
- 把 `report` / `maintenance` / `notification` / `broadcast` / `skb` 注册为工具；
- 前置 **C5**（租户跨异步传递机制）——`TenantContext` 是 ThreadLocal，长任务会丢租户；
- ⚠️ **确定性校验优先**（数字/格式用纯函数校验，LLM 只做修复提案）；**重试/幂等**是刚需。

### 3.2 **仅两项不做**

- ❌ **用户体系 / 登录 / 鉴权**（C1 / C2）
- ❌ **多租户硬化**

> demo 期按**单租户 / 显式传租户参数**运行。其余横向能力（**C3 企业级 domain、C4、C5**）**按需要做**——③ 需要 C4、② 需要 C5，属范围内。

### 3.3 内容（够用就好）

- 総務场景日语规程 + 1~2 类社内文书模板 → seed 进 SKB；
- 用**公开规章抜粋 / 假数据**，**不用真实社内事案**。

### 3.4 UI

- 复用 `admin.html`：**知识缺口审核页**（①）+ **文书生成入口**（③）+ **任务视图**（②）；
- **不做**登录页 / 角色 / 复杂交互。

---

## 4. 完成标准（每项都要达标）

| 能力 | 完成标准 |
|---|---|
| **①** | 一条 `no_match` 现场走完「捕获→起草→审核→入库」，入库后**可被检索命中** |
| **③** | 一份「数据 → 文书文件（xlsx/docx）」端到端生成并可下载 |
| **②** | 一个多步任务（如「汇总本周 X → 生成报告」）端到端跑通，**含失败重试 + 确定性校验** |
| **腿 A** | 真机核心场景稳定演示 |
| **整体** | **换来 N 场真实客户对话**（demo 的真正交付物） |

---

## 5. 时间线（到 12 月融资）

```
10/20 前后  样机到货 → 硬件团队联调（软件配合）；B 腿并行开工
10月下      ① 自生长知识端到端（约 1–2 周）
11月上      ③ 文档处理（含 C4）；商务带 demo 敲门（5–8 家 SME）
11月下      ② agent 执行（含 C5）；收集客户反馈
12月        融资包：真机 demo + 完整 B 腿 demo + 客户证据
```

> 腿 A（硬件主导）与腿 B（代码主导）**并行、互不占人**。

---

## 6. 护栏（给执行者 / agents）

1. 动手前**先在本文件确认范围**；超出 §3.1 的，**先问，不做**。
2. **保持 ①→③→② 顺序**——时间紧先保 ①③，② 是可让位项。
3. 每完成一项 → **回写基线状态**（技术基线 §6/§7 + 产品基线 §4/§9）+ **更新 `scripts/status-audit.sh` 锚点**。
4. **不引入**：代码沙箱、自动入库、登录/角色、多租户硬化——除非另行登记。
