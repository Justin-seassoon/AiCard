# 后台功能闭环差距梳理

> 日期：2026-10-24（2026-11-06 更新：补「诊断日志」，维修 / 点检随真机到位转启动）
> 范围：周报 / 月报、运营通知、知识缺口、维修 / 点检、文档处理、会议纪要、AI 任务、诊断日志
> 依据：当前代码与实际后台页面，不包含硬件能力（维修 / 点检现场闭环依赖真机，见 §6）。
> 目的：按「真实业务闭环」的标准，判断每项功能现在走到哪一步、还缺什么、大概多少工作量。
> 说明：工作量为粗估（1 人日 ≈ 1 个开发日），用于排期参考；不含用户体系（C1）与登录鉴权（C2）。

---

## 0. 结论先行

1. **当前后台功能大多停在「记录 + 状态」层**：有表、有页面、有状态流转，但没有形成「触发 → 审批 → 触达 → 执行 → 反馈 → 度量」的完整业务闭环。
2. **最缺的不是页面，而是四类连接**：
   - **角色与权限**：谁发起、谁审批、谁执行、谁可见
   - **审批与责任**：草稿 → 审核 → 发布的责任链
   - **触达与回执**：发出去没有、对方看没看、有没有确认
   - **执行与反馈**：收到之后做了什么、结果如何、是否闭环
3. **按「可演示闭环」估算**：三个重点功能（报表、通知、知识缺口）单项合计约 **16–21 人日**；如果先补共用基础（审批、分发、回执、审计），避免重复造轮子，总体约 **14–18 人日**（1 人约 3–4 周，2 人约 2 周）。
4. **按「生产可用闭环」估算**：每项约 2–4 周，且必须先补 C1 用户模型与 C2 鉴权；否则「谁审批、谁负责、谁可见」无法真实落地。
5. **建议顺序**：先补横向基础（审批状态、分发通道、回执、审计），再做各功能的执行与反馈；否则每项都要重复造轮子。

---

## 1. 闭环判定标准

| 层级 | 含义 | 典型特征 |
|---|---|---|
| **L1 数据记录** | 有表、有录入、能查询 | 后台 CRUD |
| **L2 流程状态** | 有状态机、能流转 | 待处理 → 处理中 → 完成 |
| **L3 业务闭环** | 触发 → 处理 → 审批 → 触达 → 执行 → 反馈 → 关闭 | 有责任人、有回执、有结果 |
| **L4 管理闭环** | 角色 / 权限 / 审计 / SLA / 度量 / 持续改进 | 可考核、可追责、可优化 |

当前多数功能在 **L1–L2**；本报告重点看「到 L3 还差什么」。

## 2. 总览

| 功能 | 当前层级 | 当前走到 | 缺的关键环节 | 可演示闭环 | 生产闭环 |
|---|---|---|---|---|---|
| 周报 / 月报 | L2 | 定时聚合 → 快照 → 后台查看 / 导出 | 分发、确认、行动、异常预警、权限 | 5–7 人日 | 3–4 周 |
| 运营通知 | L2 | 建通知 → 定时推送 → 投递记录 | 审批、周期执行、目标预览、失败重试、已读回执 | 5–6 人日（服务端） | 2–3 周 + 设备配合 |
| 知识缺口 | L2 | 手工捕获 → 起草 → 审核 → 入库 | 自动捕获、相似合并、分派、发布验证、复发重开、反馈 | 6–8 人日 | 2–3 周 + C1/C2 |
| 维修 / 点检 | L2 | 后台建单 → 状态流转 → 记录 | 现场上报、派单接单、现场执行、异常转维修、统计 | 5–8 人日（硬件后） | 3–4 周 |
| 文档处理 | L1 | 上传解析 → 模板生成 → 下载 | 审批、版本、编号、归档、发送、签章 | 4–6 人日 | 3–4 周 |
| 会议纪要 | L2 | 录音 → 转写 → 纪要 → 待办 → 审核 → 导出 | 待办提醒、周报聚合、参会人 / 权限、说话人分离 | 3–5 人日 | 3–4 周（含硬件） |
| AI 任务 | L1–L2 | 自然语言 → 规划 → 工具 → 产物 | 审批 / 人工确认、权限、成本控制、审计、撤销 | 3–5 人日 | 2–3 周 |
| 诊断日志 | L3 | 设备上传 → 云端存储 → 后台查询 / 下载 | —（已形成排障闭环） | 已完成 | 已可用 |

> 工作量只算服务端与后台；设备端录音、按键、回执等需硬件团队配合。

## 3. 周报 / 月报

### 3.1 现在的链路

1. 定时任务每周一 8 点、每月 1 号 8 点触发（`report/job/ReportGenerationJob.java:20,26`）
2. 遍历所有租户与设备，聚合翻译样本与问答记录（`report/service/ReportService.java:48`）
3. 指标：翻译轮次、会话数、问答命中、活跃天数、目标语言分布（`report/repository/ReportQueryService.java`）
4. 快照落库 `device_usage_report`
5. 后台按设备 / 周期查看，导出 Excel（`docgen/DocgenController.java:45`）
6. 也可以手动生成；后台要求填设备 ID（`static/admin.html:128`）

**走到的位置**：报表能自动生成、能查、能导出。属于「统计工具」。

### 3.2 闭环缺什么

| 缺口 | 现状 | 真实业务需要 |
|---|---|---|
| 统计对象 | 按设备 | 按员工 / 门店 / 团队 / 角色 |
| 指标深度 | 轮次、会话、命中、活跃 | 未命中率、低置信度占比、平均响应、热门问题、异常波动 |
| 数据可信度 | 抽样近似；会话数按连接统计 | 明确口径，或接入全量数据 |
| 分发 | 只存在后台 | 定时发给店长 / 员工（工牌、邮件、LINE 等） |
| 确认 | 无 | 已读 / 确认 / 评论 |
| 行动 | 无 | 从报表生成待办、培训、补知识 |
| 异常预警 | 无 | 用量骤降、未命中率升高时提醒 |
| 版本与更正 | 快照可覆盖 | 版本、更正记录、审批 |
| 权限 | 信任请求头 | 店长看本店、员工看本人 |
| 审计 | 无 | 谁看过、谁导出、谁修改 |

### 3.3 工作量与建议

- **可演示闭环（5–7 人日）**：
  - 增加员工 / 门店维度与 2–3 个关键指标（1–2 天）
  - 报表摘要（文字结论 + 异常提示，1 天）
  - 通过现有通知通道推送给店长（1 天）
  - 已读 / 确认 / 简单评论（1 天）
  - 从报表生成待办（复用会议待办，1 天）
- **生产闭环（3–4 周）**：C1/C2、权限、审计、数据质量、PDF / 邮件模板、异常预警、与培训 / 知识库联动。

> 一句话：现在是「报表生成器」，缺「发给谁 → 看没看 → 做了什么 → 有没有改善」。

## 4. 运营通知

### 4.1 现在的链路

1. 后台新建通知：标题、内容、源语言、目标类型（设备 / 群组）、目标 ID、触发类型、排期（`notification/controller/NotificationController.java`）
2. 轮询任务每 30 秒检查到期的单次通知并派发（`notification/job/NotificationPollingJob.java:20`）
3. 按设备语言去重翻译 + 语音合成（`notification/service/NotificationService.java:108`）
4. 通过设备推送通道下发，记录投递结果
5. 设备离线时，重连后重新合成语音补发（`NotificationService.java:92`）
6. 后台可查看投递记录、取消未发送的通知

**走到的位置**：单次通知能发到设备，有投递记录。属于「群发工具」。

### 4.2 闭环缺什么

| 缺口 | 现状 | 真实业务需要 |
|---|---|---|
| 周期通知 | 页面有「周期」选项、库里有 `cron_expr`，但**没有执行器**（只有单次派发） | 每天 / 每周固定提醒真正能跑 |
| 单次排期校验 | 未填排期时间的单次通知会一直停在待发送，也没有提示 | 创建时必填，或明确提示 |
| 审批 | 创建即生效 | 草稿 → 审核 → 定时发布 |
| 目标选择 | 手填设备 / 群组 ID | 按门店、部门、角色选人；预览人数、去重 |
| 空目标处理 | 目标解析为空时仍标记已发送 | 阻止发送并提示 |
| 已读回执 | 只有「已投递」 | 员工确认收到 / 已读 |
| 失败处理 | 失败只留空 | 失败原因、重试次数、告警 |
| 内容质量 | 机器翻译直接发 | 人工校对、术语表、模板变量 |
| 优先级 / 免打扰 | 无 | 紧急 / 普通；夜间免打扰；有效期 |
| 效果统计 | 只有投递数 | 触达率、已读率、响应率 |
| 权限 | 信任请求头；投递明细接口只按通知 ID 查，未校验租户 | 谁可以发、发给谁、审计 |
| 外部通道 | 只有工牌 | 邮件、LINE、短信等兜底 |

### 4.3 工作量与建议

- **可演示闭环（5–6 人日，服务端）**：
  - 周期通知执行器（1–2 天）
  - 审批状态与页面（1 天）
  - 目标预览 / 人数统计 / 去重（0.5 天）
  - 失败状态、重试、失败原因（1 天）
  - 模板与变量（1 天）
  - 已读回执的服务端接口（设备端另算，0.5 天）
- **生产闭环（2–3 周 + 设备配合）**：已读回执、外部通道、静默时段、优先级、效果报表、权限与审计。

> 一句话：现在是「一次性群发」，缺「审批 → 真正按时发 → 确认收到 → 看效果」。
> 注意：后台页面已经提供「周期」选项，但当前不会执行，演示时容易被问到。

## 5. 知识缺口

### 5.1 现在的链路

1. 管理员点「触发器捕获」，扫描该租户 / 门店 / 域下所有未命中的问答（`skb/curation/KnowledgeGapController.java:51`）
2. 按归一化问句做精确指纹聚合，写入缺口池（`GapCaptureService.java:34`）
3. 列表按出现次数排序
4. 管理员逐条点「起草」，系统召回相近知识，由大模型生成候选答案（`CandidateDraftService.java`）
5. 管理员点「通过入库」，系统新建一条已发布知识并写入切片（`KnowledgeGapController.java:75–95`）
6. 或点「驳回」

**走到的位置**：缺口能捕获、能起草、能人工审核、能入库。属于「知识补录工具」。

### 5.2 闭环缺什么

| 缺口 | 现状 | 真实业务需要 |
|---|---|---|
| 自动捕获 | 手工点按钮 | 定时扫描（如每天），带水位线，避免重复全量扫描 |
| 相似合并 | 只按精确指纹 | 同义句、错别字、相近问法合并；按语义聚类 |
| 优先级 / 分派 | 只按次数排序 | 指定负责人、优先级、截止时间 |
| 审核编辑 | 页面只能「通过 / 驳回」，不能改稿（接口支持传答案，页面没接） | 在线编辑、批注、多人审核 |
| 发布方式 | 每个缺口新建一条知识 | 合并到已有文档、版本管理，避免重复知识 |
| 发布验证 | 入库即结束 | 下次被问到能否命中；未命中则重开 |
| 复发处理 | 驳回后不会重开；已通过也会继续累加次数 | 驳回后复发重开；通过后统计是否真正解决 |
| 反馈 | 无 | 通知提问人 / 门店「知识已补充」 |
| 状态校验 | 无 | 防止已通过 / 已驳回的条目被重复起草、重复通过 |
| 审计 | 无审批人 | 谁审核、何时、改了什么 |
| 租户隔离 | 接口用默认租户参数（默认 1），未从登录上下文取 | 租户从身份推导，不能由调用方指定 |
| 覆盖度量 | 无 | 缺口关闭率、知识命中率、平均处理时长 |

### 5.3 工作量与建议

- **可演示闭环（6–8 人日）**：
  - 定时捕获 + 水位线（1 天）
  - 相似问法合并（1–2 天）
  - 编辑 / 批注 / 审核状态（1–2 天）
  - 发布后验证 + 复发重开（1–2 天）
  - 通知提问人 / 门店（1 天）
  - 状态机校验（0.5 天）
- **生产闭环（2–3 周 + C1/C2）**：审核人身份、多人审核、知识版本、权限、覆盖率报表、与培训 / 通知联动。

> 一句话：现在是「补一条知识」，缺「谁负责补 → 补得对不对 → 有没有真的被用上 → 没解决怎么办」。

## 7. 其他功能（简评）

### 7.1 文档处理

- **当前**：上传 Excel / CSV → 解析预览；选 6 类模板 → 生成 Word / Excel → 下载（`docgen/DocgenController.java`）。
- **缺口**：模板管理、编号规则、审批、版本、归档、发送、签章、OCR / 扫描件、导入业务系统。
- **判断**：是「文档生成工具」，不是「文档流程」。
- **工作量**：可演示闭环 4–6 人日；生产级 3–4 周。

### 7.2 会议纪要

- **当前**：录音 / 导入 → 转写 → 结构化纪要 → 待办（含负责人 / 期限 / 状态）→ 审核 → 导出。
- **缺口**：待办提醒与催办、纪要转周报、参会人与知情确认、权限与分享、说话人分离、搜索归档。
- **判断**：链路最接近闭环，但停在「审核 + 导出」，待办没有回到执行。
- **工作量**：可演示闭环 3–5 人日（待办提醒 + 周报聚合）；生产级 3–4 周（含真机录音）。

### 7.3 AI 任务

- **当前**：自然语言 → 规划工具序列 → 执行 → 校验 / 重试 → 产物。
- **缺口**：高风险操作的人工确认、权限、成本上限、审计、撤销、定时 / 周期任务。
- **判断**：是「执行工具」，不是业务闭环本身；它的价值取决于被调用的业务工具是否闭环。
- **工作量**：可演示护栏 3–5 人日；生产级 2–3 周。

### 7.4 诊断日志

- **当前**：设备上传（文本 / JSONL，gzip，单次 ≤256KB）→ 云端存共享卷 + DB 索引 → 后台按设备 / 会议 / 时间查询、一键下载最新日志（`admin.html`「诊断日志」页签）。
- **缺口**：—（已形成「出问题 → 传日志 → 取日志」的排障闭环）。
- **判断**：后台 9 项功能中唯一相对闭环的；后续可补纯设备 token 的下载接口、日志告警 / 聚合分析。
- **工作量**：已可用；增量（设备侧下载接口约 0.5 人日）视需要。

## 8. 横向缺口（所有功能共有）

| 缺口 | 影响 | 说明 |
|---|---|---|
| **C1 用户模型** | 所有「谁」都无法落地 | 报表按设备、通知按设备、审批无审批人；需要 `app_user` 与员工 / 门店 / 角色关联 |
| **C2 登录鉴权** | 权限与审计不可信 | 当前信任请求头，任何人可改租户；审批、导出、发送都无法追责 |
| **租户隔离** | 部分接口可越权 | 知识缺口接口用默认租户参数；通知投递明细未按租户校验 |
| **设备回执** | 通知 / 报表的「已读」无法闭环 | 需要设备端确认消息（按键 / 语音）与上报 |
| **统一审批状态** | 各功能重复实现 | 建议抽「草稿 → 待审 → 已发布 / 已驳回」通用状态与页面 |
| **统一分发通道** | 报表、通知、待办各自为政 | 工牌推送、邮件、LINE 等统一出口，带投递 / 已读状态 |
| **审计日志** | 出问题无法追溯 | 记录创建、审批、发送、导出、修改 |
| **定时调度** | 部分功能只能手工触发 | 知识缺口捕获、周期通知尚未接入调度 |
| **数据质量** | 报表与知识缺口数字不可信 | 抽样、会话口径、时区、设备即人 |

## 9. 建议实施顺序

### 阶段一：补横向基础（约 4–6 人日）

1. 通用「草稿 → 待审 → 已发布 / 已驳回」状态与审批页面
2. 统一分发接口（工牌 + 邮件 / 导出链接），带投递状态
3. 审计日志（谁在何时做了什么）
4. 定时任务统一接入（知识缺口捕获、周期通知）

### 阶段二：三个重点功能补闭环（约 10–12 人日）

1. **知识缺口**：定时捕获 → 相似合并 → 编辑审核 → 发布验证 → 复发重开 → 通知提问人
2. **运营通知**：审批 → 周期执行 → 目标预览 → 失败重试 → 服务端已读接口
3. **周报 / 月报**：员工 / 门店维度 → 关键指标 → 摘要 → 推送店长 → 确认 / 评论 → 生成待办

### 阶段三：执行侧闭环（真机已到位，约 5–8 人日 + 硬件）

1. 维修 / 点检：现场上报 → 派单接单 → 现场执行 → 验收 → 异常转维修（下周启动最小闭环）
2. 会议待办：提醒 / 催办 → 周报聚合
3. 通知 / 报表的设备端已读回执

### 阶段四：生产化（3–4 个月，含 C1/C2）

用户模型、登录鉴权、角色权限、SLA、效果度量、外部通道、数据质量。

---

## 10. 一句话总结

**现在的后台是「一堆能用的工具」；真实业务闭环缺的是「人、责任、触达、反馈」这四件事。** 页面和接口已经够演示，但要让客户相信「用了就能管起来」，下一步应优先补横向的审批、分发、回执、审计，再把每个功能的执行侧接上。
