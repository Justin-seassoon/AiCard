第一部分：8201 内存不足 —— 四方案评审

一、问题背景

  • 现状：楼氏 IA8201 SRAM 仅 1.44MB，同时加载「全双工 AEC + 4 麦 Beamforming + VAD + KWS」时，DSP 的 Data / Instruction Memory 溢出。
  • 核心目标：在保障「4 麦波束成形 + 基础 AEC」不被打折的前提下解决溢出（注：PRD 定位为连续轮流对话，不承诺全双工打断）。
  • 前置问题① 内存账未算：三份材料均无量化：AEC 滤波器阶数 × 延迟线、4 麦 BF 频域系数、KWS 模型权重、VAD 各自 SRAM 占用与溢出量都没算。应先向楼氏要内存预算表，再谈「卸载哪个算法」。
  • 前置问题② 存储受限而非算力受限：16kHz 采样对 IA8201 算力富余很大，溢出的本质是「静态存储」（KWS 权重 / AEC 长滤波器 / BF 系数），不是实时算力。正确方向是减存储 / 降模型 / 剪系数，而非「卸载算法省算力」。

二、四方案逐一评估

  • 方案① VAD 卸载至 P4：架构解耦、改动最小，但功耗 + 音频源两坑未解。
  • 原理：8201 只保留轻量「能量阈值检测」，超阈值即经 GPIO 硬件中断唤醒 P4 的 LP-Core / HP 核心，由 P4 运行 ESP-SR AI-VAD 做人声判定，为 8201 释放内存。
  • 判断：VAD 只需「有没有人声」、不需多麦信号，放主控方向合理；但把 always-on 的 VAD 从低功耗 DSP 挪到高功耗 P4，与「待机 7–10 天」硬指标背道而驰——LP-core 需常开、HP 被频繁唤醒，功耗账大概率崩。「改动最小」只算了软件改动、没算功耗。
  • 隐患：① 能量阈值在嘈杂前台误触发 → P4 频繁唤醒；② P4 跑 AI-VAD 需一路能抓「游客远端语音」的音频——耳麦那路是员工近讲、抓不到 0.5–1.5m 外的游客，不能救 VAD，需 SPI 回传或单路麦直连。
  • 方案② Overlay + BF 剪裁：剪裁对，Overlay 首音空窗需正视。
  • 原理：待机只加载 VAD + 极简降噪，VAD 触发后经 SPI 动态覆写加载 AEC + BF；BF 频段从全频段剪到 300Hz–3.4kHz 人声核心频段。
  • 判断：频段剪裁正确：协议 16kHz，奈奎斯特上限才 8kHz，剪到人声频段损失小、系数矩阵省内存。但坑不在「AEC 收敛期」，而在「VAD 触发 → 加载完成期间，采集语音无 BF 无 AEC → 首字丢失 + 处理空窗」。
  • 隐患：① 能量 VAD 误触发 → 反复加载 / 卸载 AEC+BF → 系统抖动；② Overlay 是 DSP 底层内存覆写，强依赖楼氏 FAE，加载时间（代码段 + 系数段）需实测。
  • 方案③ 双通道固定波束：真降级，但降级原因要说清。
  • 原理：4 麦全自适应 BF →「固定空间波束 + 双通道物理差分」，靠上 / 前麦 15° 开孔物理隔离，宣称 >18dB 通道隔离度。
  • 判断：「18dB 隔离度」是声学物理隔离 / 串扰指标，与「波束降噪能力」是两回事，不能混。真正的降级是「4 麦 → 2 麦」：阵列增益减半、丢失空间自由度，且双麦差分在低频端（麦间距 ≪ 波长）需白噪声增益补偿，会放大低频环境噪声。
  • 隐患：工牌方向基本固定、本就不需自适应方向追踪；但 0.5–1.5m 远场下信噪比掉一档，直接传导到 ASR 识别率 → 翻译质量。
  • 方案④ 换芯片 / 外挂 PSRAM：兜底，但「外挂 PSRAM」大概率是伪命题。
  • 原理：切楼氏下一代大内存 DSP（IA8508）或外挂 SPI PSRAM / SRAM。
  • 判断：IA8201 是片上 SRAM、数据内存总线不外扩；外部 SPI Flash 只能存代码（Overlay 加载源）、不能当运行期 Data Memory。DSP 核高速访问的系数 / 延迟线必须落片上 SRAM。「外挂 PSRAM 解决 Data Memory 溢出」大概率不成立，需楼氏一票否决。
  • 隐患：换芯片重选型拉长 EVT + 增 BOM；原理图 9.15 冻结，决策窗口只剩几天。

三、推荐组合与结论

  • P0 先做：向楼氏要两张表：①内存预算表（AEC / BF / KWS / VAD 各占多少、溢出量）②硬件能力（有无外扩 Data Memory 总线、满配 4 麦后有无空余音频输入接耳麦）。没有这两张表，一切方案悬空。
  • P1 高收益：砍 KWS / 降级为按键唤醒（KWS 模型权重 100–500KB 级，是内存大头、比 VAD 大得多；1.0 交互本就是短按翻译键触发）；VAD 退化为逐帧能量断句留在 8201，AI-VAD 神经网络移除 / 极简（断句只需能量 / 过零率，不需神经网络）。
  • P2 低成本：BF 频段剪裁至 300Hz–3.4kHz；Overlay 只做「系数段」动态加载 + 环形缓冲重放兜底首字丢失。
  • P3 兜底：VAD 卸载至 P4 仅在 P0 证明内存仍不够、且功耗账算得过时启用；双通道固定波束（方案③）真降级，仅兜底。

四、双方此前都遗漏的关键点

  • KWS 是内存大头：唤醒词神经网络权重 100–500KB 级，远大于 VAD；1.0 由按键触发，KWS 更像加分项，可砍 / 降级。
  • AI-VAD 可能是伪需求：会话由按键触发，VAD 的作用是 1.2s 静音断句，逐帧能量 / 过零率检测即可，无需神经网络。
  • 采样时钟漂移：跨芯片 AEC 的真正杀手：P4 与 8201 若不同晶振 / PLL，参考与近端会长期相位漂移、AEC 发散，需确认能否共享声钟（BCLK / LRCLK）。
  • 参考信号取样点：AEC 参考应取功放前级（DAC 数字 / Codec 前级），而非喇叭端模拟（会引入功放非线性）；且需确认 8201 Reference Input 是数字还是模拟。
第二部分：耳麦回声风险评审

一、问题本质：先分两条回声路径，再谈三层递进

  • 两条回声路径：路径 A：喇叭 → 4 麦（污染游客语音 ASR）；路径 B：喇叭 → 耳麦（真打断要处理的回声）。两者是不同问题，Loopback 只对 A 有效。
  • 回声消除 AEC：需「参考信号 + 近端信号」两路，汇入同一 AEC 引擎、在同一采样时钟下对齐。
  • 打断 Barge-in：员工在播报途中开口，设备停播并转采员工语音；依赖 AEC 成立。
  • 采播互斥（兜底）：播时不采、播完再采，防啸叫但放弃打断；PRD 定位「连续轮流对话」，本就允许此形态。

二、为什么「大模型按语种处理」不可行

  • 时序错位：回声是音频波形层的物理叠加，语种是语义层信息；AEC 必须先于 ASR / 语种判定完成，语种信息来不及参与。
  • 判出语种也抠不掉：回声是外放音经空气 / 机壳反射回来的「延迟副本」，与员工真实语音叠加在同一路采样里，靠语种无法把叠加分量分离。
  • 反向依赖：AEC 没做会污染输入，ASR 和语种判定自己都失真——语种这个「事后信息」反而依赖回声这个「事前问题」先解决。

三、甲方 Loopback 方案评估

  • 对路径 A 有效（该做）：从 Smart PA DAC 引参考线入 8201 Reference Input，配合 4 麦近端，8201 内可闭环消除 TTS 对游客 ASR 的污染——这条必须做、且能做。
  • 对路径 B 无效（漏洞）：耳麦近端在 P4、参考线在 8201，P4 侧没有参考信号，AEC 不闭环，「真打断」没兑现。甲方用解决 A 的方案回答 B 的问题，答非所问。
  • 甲方已自认：「P4 软件做简单侧音抑制」≈ 采播互斥：外放时压低耳麦增益 / 静音，员工开口被一起压掉。

四、可行方案（优 → 劣）

  • ① 耳麦引入 8201（真打断正解，但有硬件前提）：近端 + 参考两路都在 8201，完整 AEC。前提：IA8201 满配 4 路 PDM 后仍有空余 I2S 输入可接耳麦——若无，此方案硬件上不可行，须 9.15 前让楼氏给确定性答复。
  • ② 参考分路 P4 做 AEC：技术可行（AEC 不要求物理同芯片、只要求同钟对齐），但 P4 上 FreeRTOS + Wi-Fi 下音频中断的确定性时延难保证，且与 8201 的采样时钟漂移需解决，不推荐。
  • ③ 采播互斥 / 侧音抑制兜底：防啸叫、牺牲打断；不违背 PRD（连续轮流对话），若①因硬件做不了，1.0 走此档并降级「打断」验收项。
方案能否真打断时延/算力开发难度定位
① 耳麦引入 8201能最优（专用 DSP）低-中（改电路）正解，须确认硬件

五、与「VAD 卸载至 P4」的耦合（如何化解）

  • 原耦合：耳麦在 P4 + AI-VAD 也放 P4 → VAD 用耳麦信号，但耳麦抓不到游客语音、又混了 TTS 回声，VAD 会失灵。
  • 化解：按「AI-VAD 移除、逐帧能量断句留 8201」的新方向，此耦合反而解除——VAD 不再依赖 P4 的音频源。
  • 结论：优先走「能量断句留 8201」，一举规避音频源 + 功耗两个坑。

六、9.15 原理图冻结前需决策的硬件项

  • 真正需冻结前确认的是两个纯硬件问题：①IA8201 有无空余音频输入接耳麦 ②有无外扩数据内存总线。
  • 「真打断」是加分项、非 PRD 1.0 基线；若耳麦进不了 8201，走采播互斥兜底，不违背 PRD，无需为此在窗口期内做可能做不成的硬件改动。

七、云侧立场

  • 云侧不做回声消除，这是端侧实时职责（已于 9.13 例会确认由端侧负责）；云侧只配合协议。
  • 端侧做到真 AEC → 云侧按「打断」模式配合（播放中收到员工语音即停播、切采集）。
  • 端侧只能采播互斥 → 云侧按「播完再采」降级验收，并把「打断」从联调必测项明确降级。
