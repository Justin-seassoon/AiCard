「主动与执行（远景）」落地可行性分析报告
日期：2026-09-20
范围：演示控制台「远」步所展示的全部 10 个「主动 → 执行 → 记忆」场景（连锁酒店 / 免税店 / 机场 / 工地 / 劳务派遣 / 制造 / 餐饮 / 农业 / 介护 / 清扫）
目的：评估每个场景在 1.0 端侧硬件 + 现有云端架构 约束下的真实落地难度，为「演示愿景」到「可交付功能」提供取舍依据。

一、结论先行（TL;DR）

  1. 三种能力落地难度差异极大，不能混为一谈：
  • 记忆（记住）：纯云端数据存储，现已具备（postgres + 四层租户隔离），✅ 全部可行。
  • 执行（连系统办）：分两类——「云端自有能力」（表单 / 工单 / 通知 / 台账 / 统计）✅ 1.0 就能做；「对接企业/第三方系统」（PMS / POS / GDS / 呼叫 / 税务）🔴 高门槛，1.0 大概率降级为「生成工单转人工」。
  • 主动（提前提醒）：受端侧「会话级短连接 + 7–10 天 Deep Sleep 待机」与「实时推送」的根本矛盾制约，🟡 是最大卡点，需做架构取舍。
  1. 核心矛盾（一句话）：主动提醒要求设备「随时可被云端触达」，但 1.0 端侧为省电待机时无长连接、无心跳。所以「主动」要么只在设备在线时触发（窗口窄），要么让设备定时醒来轮询（牺牲待机），要么改硬件（1.0 板子无余量）。
  1. 日本中小企业系统 API 普遍缺失是「执行」的第二大卡点：PMS/POS/GDS 等封闭或收费，介护/考勤有成熟云服务但开放 API 的少。1.0 落地应把「执行」聚焦在云端自有台账/工单/通知，对接外部系统一律延后。

二、评估口径（统一框架）

2.1 三能力评级定义

评级含义判断标准
✅ 可行现有架构/硬件即可实现，无需新基建纯云端存储、云端自有流程、已有推送通道（在线时）
🟡 有条件可行需降级、或需端侧/商务配合、或有明显取舍实时推送→轮询；对接系统→转人工；需端侧加定时唤醒
🔴 高门槛1.0 大概率做不了，需外部 API/商务/硬件改造PMS/POS/GDS/呼叫/税务对接；长连接/常开唤醒

2.2 端侧硬件现实（交互可行性的基础）

来自 PRD §7 与已冻结协议：

硬件能力现状对「主动提醒」的影响
显示彩屏，无触屏，有方向键+确认键可显示短文字/图标/菜单，支持菜单式交互；复杂多语言受本地字体库限制
播报扬声器 TTS 外放（设备只播 TTS、不显示翻译文本）主动提醒最自然载体，但打扰性强（客人面前、安静环境）
提示LED 指示灯只能表达「有消息」，无法传内容，需配合按键拉取
输入翻译键 + 高频语言键 + 方向键 + 确认键（无触屏）可通过方向键+确认键做菜单式交互（查看任务/稍后提醒/确认完成）；长文本仍需后端/App
采集4 麦阵列 + VAD（静音 1.2s 断句）+ AEC与提醒无关
功耗待机 7–10 天（Deep Sleep），1500mAh硬约束：不能常开长连接/心跳
通信双频 Wi-Fi（可选 4G Cat.1）；会话级短连接，睡眠前上报 sleep_notice待机时云端无法触达设备

2.3 「主动推送」的三种技术路径（关键取舍）

路径机制实时性功耗代价可行性
A. 在线触发设备在会话中 / 刚按键唤醒后，云端即时下发实时（0 延迟）无额外代价✅ 立即可做，但窗口窄（员工大部分时间待机）
B. 定时轮询设备每 N 分钟醒来，Wi-Fi 连一次查待办再睡延迟 ≈ N/2~N 分钟每次唤醒 1–2s 连接 + HTTP；N 越小越耗电🟡 需端侧固件配合，与 7–10 天待机 trade-off
C. 常开低功耗心跳BLE/低频保活，云端实时触达实时需 BLE 常开/网关🔴 1.0 板子无余量（BLE 仅预留配网）
判断：1.0「主动提醒」的现实形态是 A 为主（在线时即时推送）+ B 折中（离线补拉，复用广播的「准实时 + 离线补拉」模型）。真正的「实时主动触达」是 1.0 之后的硬件/协议议题。

四、跨场景共性结论

4.1 数据接入是「执行」的普遍卡点

10 个场景里，「连系统办」的多数动作（查空房/开退税单/改签/呼叫支援/补货/失物）都依赖一个封闭或管制的外部系统。日本中小企业普遍无开放 API，所以：

1.0 落地的正确姿势：把「执行」聚焦在云端自有能力（表单、工单、通知、台账、统计、回执）——这些不依赖任何外部系统，现在就能做；「对接企业系统」一律标注为 P2（需商务 + API），并用「生成工单转人工」兜底。

4.2 「主动提醒」在端侧的现实形态

  • 最可行：有明确、免费触发源的场景——工地/农业的天气预警、介护的定时翻身服药、制造/清扫的定时点检检查。这些要么是「定时任务」，要么有免费 API。
  • 绕开矛盾：提醒对象是管理方的场景（劳务派遣的在留续签），可用后台/App 推送，不必占用端侧实时通道。
  • 必须端侧配合：真正的「实时主动触达」需要端侧支持定时轮询唤醒（路径 B），或未来硬件加低功耗保活（路径 C）。这是与 7–10 天待机的量化 trade-off，需端侧共同拍板。

4.3 交互友好性（基于现有硬件）的关键判断

提醒类型呈现方式友好性备注
短指令（停工/补货/翻身）TTS 外放 1 句话🟡 中最直接，但打扰；建议「LED 提示 → 员工按键 → 才播 TTS」的拉取式更礼貌
待办/清单彩屏菜单 + LED🟡 中彩屏可显示待办菜单，方向键浏览；但员工未必低头看
长内容/表单均不适合🔴无触屏、无键盘，长表单必须走后端/App
建议：主动提醒默认走 「LED 亮 + 彩屏图标/菜单 → 员工方向键选择或按键 → TTS 播报内容 → 确认键回执」 的链路，避免在客人面前突然外放（尤其酒店/免税/介护等礼貌敏感场景）。这要求端侧支持「提醒队列 + 按键拉取播报」，属端侧配合项。

五、1.0 落地优先级建议（Roadmap）

优先级内容说明
P0（现在就能做，无需新基建）① 全部「记忆」能力；②「执行」的云端自有部分（表单/工单/通知/台账/统计/回执）；③「主动」的在线时触发（复用现有 WSS + 广播通道）纯云端 + 已有通道
P1（需端侧固件配合）④ 定时轮询唤醒（路径 B，折中功耗）；⑤ 彩屏待办菜单 + 方向键/按键拉取播报需端侧拍板「功耗 vs 实时」量化指标
P2（需商务 + API）⑥ 对接企业系统（PMS/POS/GDS/呼叫/免税/介护软件）；⑦ 天气/交通等免费第三方 API 接入逐家谈商务，1.0 后用「工单转人工」兜底
P3（需硬件改造）⑧ 低功耗保活心跳（路径 C）1.0 板子无余量，V2 评估

六、风险与开放问题

  1. 功耗 vs 实时性的量化：若走「定时轮询」，N 取多少？需端侧实测「每次唤醒耗电」与「7–10 天待机」的关系，给出「N=5min 待机缩到 X 天」的曲线，才能拍板。
  2. 打扰与礼仪合规：日本服务业在客人面前外放提醒可能泄露客人信息、不礼貌。需设计「静默提示 + 按键拉取」的默认交互，并允许员工关闭语音。
  3. 隐私合规：采集客人偏好、介护病史（属「要配慮個人情報」）、劳工数据，需满足日本《个人情报保护法（APPI）》的同意取得 + 安全管理措施 + 数据最小化。
  4. 数据来源真实性：1.0 大量数据靠「人肉录入/Excel 导入」，存在「录入滞后 → 提醒失真」的风险，需在演示与真实部署中明确区分。
  5. 提醒触达窗口窄：路径 A（在线触发）下，员工大部分时间待机，提醒大概率「延迟到下次按键才送达」，需向演示/客户如实说明这是「准实时」而非「秒级实时」。
