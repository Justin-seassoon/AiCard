## 0. 三条原则

1. **迁移 = 真源**。改 schema 一律**加迁移**（`V{next}__xxx.sql`），**不要手改库**。
2. **一致性守卫**：JPA 实体 + `spring.jpa.hibernate.ddl-auto=validate`——实体与库不一致时**启动即报错**，库难偷偷漂移。
3. **本文件是摘要**：表清单 + 用途 + 关系 + 迁移归属；**字段级真相在迁移**。

## 2. 租户隔离模型（关键）

```
customer （租户）
  └── store （门店）
        └── device （设备；device_id 全局唯一）
```

- **所有业务表带 `customer_id` + `store_id`**，仓储查询强制从 `TenantContext` 取租户过滤。
- 例外：`device_group_member` / `broadcast_delivery` / `notification_delivery` 通过 `device_id` 间接关联；`ota_*` / `system_config` 为全局或分级。
- ⚠️ 已知限制见技术基线 §4（C3：租户强制绑 store；C1：无用户表）。

## 4. 关键关系与约定

- **租户边界**：`customer_id` + `store_id` 是绝大多数表的复合索引前缀。
- **唯一键**：`device.device_id`、`customer.code`、`store.code`、`document` 无、`device_usage_report(device_id,period_type,period_start)`、`system_config(customer_id,store_id,config_key)`、`meeting.meeting_id`、`meeting_chunk(meeting_id,seq)`。
- **软删除/状态**：`document.status`、`maintenance_order.status`、`operation_notification.status`、`meeting.status`、`meeting_action_item.status`——均为 `VARCHAR` 状态字段（非枚举表）。
- **JSON 字段**：`inspection_task.checklist`、`inspection_record.results`、`device_usage_report.metrics`、`meeting.missing_seqs` / `transcript_json` / `minutes_json`。
