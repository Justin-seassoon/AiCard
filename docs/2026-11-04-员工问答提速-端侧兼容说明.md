# 员工问答（staff_qa）提速 · 端侧兼容说明

> 版本：v1（2026-11-04）｜ 面向：ODM 端侧固件团队 ｜ 关联协议：《端云通信协议-唯一基线》v15 §2.4.2、§2.7.3
> 结论先行：**WSS 协议与帧结构不变，端侧不改代码也能兼容**；但有 **2 条必须确认**（首帧 WAV 头长度字段为 0、stop_tts 期间的帧丢弃），见 §4。

---

## 1. 本次改了什么（云端）

| # | 改动 | 对端侧可见性 |
|---|---|---|
| 1 | 答案 TTS 由「整段合成完再下发」改为「边合成边下发」 | **可见**：`0x81` 首帧到达时间提前；首帧 WAV 头长度字段为 0 |
| 2 | 语音识别由「eou 后整段识别」改为「边说边识别」 | 不可见：上行帧格式与 eou 语义不变 |
| 3 | 高频问答答案缓存（5 分钟 + 知识库写入即失效） | 部分可见：相同问题第二次起 `answer` 帧明显更快 |
| 4 | 检索/生成分段计时、质量评测工具 | 不可见 |

协议版本仍为 WSS v1，`proto_ver=1` 不变。

## 2. 改造前后的时序对比

改造前（首音频要等整段 TTS 合成）：

```
eou ──► ASR 1.0~1.3s ──► 检索+LLM+校验 2.5~4.4s ──► answer
                                                      │ 整段 TTS 合成 0.4~1.5s
                                                      ▼
                                          0x81 ×N（一次性连发）──► tts_end
```

改造后（边合成边下发，缓存命中时检索/LLM 基本为 0）：

```
eou ──► ASR 0.26~0.42s ──► 检索+LLM+校验（缓存命中 ~0ms）──► answer
                                                      │ 0.25~0.44s
                                                      ▼
                                          0x81 首帧 ──► 分片连续下发 ──► tts_end
```

端侧感知：`answer` 与首个 `0x81` 之间的间隔从 **0.4~1.5s 缩短到 0.25~0.45s**；缓存命中时整轮从 ~4s 降到 **~0.7~0.9s**。

## 3. 下行 TTS 帧的实际内容（测试服抓包实录）

帧结构完全遵循协议 §2.4.2，未新增字段：

```
0     1 byte    frame_type = 0x81
1     1 byte    turn_id_len = N
2     N bytes   turn_id (UTF-8)
2+N   剩余       tts_audio
```

实测样例（普通话答案，3.6 秒语音）：

| 帧 | 音频负载 | 内容 |
|---|---|---|
| 第 1 帧 | 8000 字节 | **44 字节 WAV 头 + 7956 字节 PCM16** |
| 第 2…14 帧 | 8000 字节 | 纯 PCM16（无头） |
| 第 15 帧 | 4300 字节 | 纯 PCM16（末帧可短于 8000） |

合计音频负载 116,300 字节（≈3.6 秒语音），帧头每个额外 5 字节（`0x81` + `turn_id_len` + `turn_id`）。

首帧 WAV 头字段（**与改造前的唯一差异**）：

| 字段 | 改造前 | 改造后 |
|---|---|---|
| `RIFF` / `WAVE` / `fmt ` / `data` 标记 | 正常 | 正常 |
| RIFF 长度（offset 4） | 真实总长 | **36**（长度未知占位） |
| `data` 长度（offset 40） | 真实 PCM 长度 | **0**（长度未知占位） |
| 采样格式 | PCM16 · 16kHz · 单声道 | 不变 |

> 改造前 WAV 头里的长度是"整段音频"的真实值；现在边合成边发，云端**在发首帧时还不知道总长**，所以写 0。音频结束的唯一权威信号是 JSON `tts_end`（协议原本就这么规定）。

## 4. 端侧要求（R1–R6）

| 编号 | 要求 | 说明 |
|---|---|---|
| **R1** | **只跳过首帧的 44 字节 WAV 头**，后续帧不得再跳 | 与现有实现一致；如按"每帧都检查 RIFF 再跳"也要能正确跳过 |
| **R2** | **不得依赖 WAV 头的 RIFF / data 长度字段** | 现在为 0。若固件用 `dataSize` 预分配缓冲、算时长或驱动进度条，**必须改为忽略**，以 `tts_end` 判结束、按实际收到字节数统计 |
| **R3** | 收到首个 `0x81` 即进入播放（可先缓冲 1~2 帧或 ~200ms 再启动） | 首帧即含约 250ms 音频；不要等待固定时长或"合成完成"标志 |
| **R4** | 播放中触发 `stop_tts`（按键/新语音）时，**本地停播并丢弃同 `turn_id` 的后续 `0x81`，直到收到 `tts_end`** | 云端对 staff_qa 的 `stop_tts` 尚未做服务端停发（已知缺口，后续版本补）；流式下云端会继续推完剩余分片，端侧必须自行丢弃，避免"停了又响" |
| **R5** | 上行保持不变；每轮**必须发 `eou`** | 云端在首个音频分片到达时即开始流式识别，`eou` 用于收口取最终文本；未发 `eou` 的轮次不会产生答案（云端会在下一轮自动取消残留识别会话） |
| **R6** | 不要依赖 `answer` 与首个 `0x81` 之间的固定间隔 | 该间隔现在更短（0.25~0.45s），且缓存命中时 `answer` 本身更快；按"收到就处理"实现即可 |

### 缓冲需求说明

单轮答案的音频总量不变（约 100~260KB，对应 3~8 秒语音），且**改造前后都是以"快于实时"的节奏连发**——改造前是合成完一次性连发，现在是合成一点发一点。因此**峰值缓冲需求与原来相同**，无需增大缓冲；区别只是到达更早。

## 5. 兼容性回退（如 R2 短期无法确认）

若固件确实依赖 WAV 长度字段、短期无法修改，云端可提供**服务端开关**临时回退为「整段合成后再下发」（首帧 WAV 头写真实长度，行为与改造前一致）。

- 状态：**尚未实现，按需开发**（约 0.5 人日，含回归）。
- 影响：回退后首音频延迟恢复为改造前水平（约多 0.2~0.4s），其余不变。

请端侧在 §7 回签表中说明是否需要该开关。

## 8. 常见问题

**Q1：首帧 WAV 头长度是 0，会不会导致播放器判定为 0 秒直接结束？**
A：取决于固件解析方式。只"跳过 44 字节 + 播放收到字节"的实现不受影响；若读取长度字段就必须改（R2）。

**Q2：能不能不等 `tts_end`，用"音频流多久没新帧"判断结束？**
A：不建议。合成速度与网络抖动会制造空档；`tts_end` 是协议规定的唯一结束信号。

**Q3：会不会一帧超过 8KB？**
A：不会，单帧音频负载上限 8000 字节（协议 §9），刚抓包验证过。

**Q4：打断后云端还会继续发帧吗？**
A：会（staff_qa 的 `stop_tts` 服务端处理尚未实现）。端侧按 R4 丢弃即可，无需断开连接。
