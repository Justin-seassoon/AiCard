AI 工牌 1.0 · 对甲方建议的评价与建议
8201 内存不足 + 耳麦回声 · 2026-09-12 · 用于三方周例会

一、总体评价

甲方这份建议整体专业、务实，方向正确。四个方案从「改动最小」到「最后兜底」分层递进、逻辑清晰，且始终锚定「4 麦波束成形 + AEC 强打断这两个核心体验指标不被打折」，说明对产品诉求有清晰把握。尤其是否定「用大模型按语种处理回声」、提出「Loopback 参考线」，这两处判断很到位。我们高度认同，并在甲方方案基础上补充几点建议，供一起把方案做实。

二、值得肯定的几点

  • 1. 「架构解耦与算力重分配」的大方向是对的：把 VAD（只需判断「有没有人声」、不需要多麦信号）从音频 DSP 挪到主控，是合理的解耦思路，我们赞成。
  • 2. 方案②的波束频段剪裁是有效的省内存手段：本项目协议就是 16kHz 采样，奈奎斯特上限仅 8kHz，把波束成形剪到 300Hz–3.4kHz 人声核心频段，损失很小、系数矩阵能实打实省内存。
  • 3. 否定「大模型按语种处理回声」是对的：回声消除必须在端侧几百毫秒内实时完成，云端 LLM 的时延和语义信息都来不及参与这个物理层处理。这一点我们完全同意。
  • 4. Loopback 参考线的方向正确：AEC 要成立，必须先有「外放参考音」这一路输入，这是标准做法。
  • 5. 配网选 C5 的 Soft-AP + BLE 混合模式：符合日本企业 Wi-Fi 的合规要求，我们认同。

三、建议进一步对齐的几点

  • 1. 建议先以楼氏的内存预算表为准：当前「释放 30–40%」是基于 VAD 占用比例的估计，但 1.44MB 里 AEC、4 麦 BF 系数、KWS 权重、VAD 各自的真实占用还没有量化数字。建议请楼氏先出一张内存预算表，明确「谁占最多、溢出多少」，再定卸载 / 剪裁哪个算法，避免方向对了、但省得不够。
  • 2. 方案④的「外挂 PSRAM」，建议先向楼氏确认一个前提：IA8201 这类低功耗音频 DSP 的 SRAM 通常为片上资源，数据内存总线可能不对外扩展，外部 SPI Flash 一般只能存代码、不能当运行期数据内存用。若确认数据总线不外扩，「外挂 PSRAM」这一路就走不通，方案④就只剩「换更大内存芯片」一种，需提前评估对 EVT 周期和 BOM 的影响。
  • 3. 方案③的「18dB 通道隔离度」，建议澄清一下口径：18dB 通常指麦克风开孔带来的声学物理隔离 / 串扰指标，与「波束成形算法的降噪增益」是两个不同概念。固定波束在方向基本固定的工牌场景是够用的，真正的取舍是「4 麦降到 2 麦会损失约一半阵列增益」、以及双麦差分在远场低频会放大噪声。建议把方案③的代价表述清楚，便于评估它作为降级手段是否值得。
  • 4. 方案①「VAD 卸载至 P4」，建议补一项评估——待机功耗：把 always-on 的 VAD 从低功耗 DSP 挪到主控，意味着主控 LP 核常开、高频被唤醒，这与 PRD「待机 7–10 天」的硬指标需要一起算账。建议在锁定方案①前，补一个「主控常开跑 VAD 的电流实测」，确认功耗可接受。
  • 5. 耳麦回声，建议把两条回声路径分开看：Loopback 参考线解决的是「扬声器外放污染 4 麦、影响游客语音识别」这一路——这条必须做、也做得到；而「员工戴耳麦开口打断外放」是另一路，需要耳麦的近端信号也进入做 AEC 的处理器。目前耳麦接在 P4、参考线进 8201，两路不在同一处理器，耳麦这一路的「真打断」暂无法闭环。建议在 9.15 冻结前向楼氏确认：IA8201 满配 4 路麦克风后，是否还有空余音频输入可接耳麦——这决定了 1.0 是落地「真打断」，还是先以「采播互斥」兜底（后者不违背 PRD「连续轮流对话」的定位）。

四、我们的补充建议

  • 1. KWS 值得重新评估：唤醒词神经网络模型往往是内存占用的大头（可达数百 KB，远大于 VAD）。而 1.0 交互以「短按翻译键」触发为主，KWS 属于加分项。若内存确实紧张，优先考虑「砍掉 KWS 或降级为按键唤醒」，释放的内存可能比卸载 VAD 更可观。
  • 2. VAD 不必用神经网络：翻译场景里 VAD 的作用是「1.2 秒静音断句」，逐帧能量 / 过零率检测即可胜任，无需 AI-VAD。把「逐帧能量断句」留在 8201（延迟最低），AI-VAD 可直接移除——既省内存，又规避了主控功耗和音频源两个问题。
  • 3. 跨芯片协同的时钟同步：若最终需 P4 与 8201 协同做音频处理，建议确认两者能否共享同一声钟（BCLK / LRCLK），避免采样时钟漂移导致 AEC 长期发散。
  • 4. 参考信号取样点：Loopback 参考信号建议取「功放前级（DAC 数字 / Codec 前级）」，而非喇叭驱动后的模拟信号（会引入功放非线性），同时确认 8201 的 Reference Input 是数字还是模拟接口。

五、小结

甲方的建议方向正确、值得采纳。我们建议在「方案①（VAD 解耦）+ 方案②（BF 剪裁 / Overlay）」的主线上推进，同时请楼氏先补齐「内存预算表」和「硬件能力边界」两张关键信息，再锁定最终方案；耳麦这一路，以「能否进 8201」作为 9.15 冻结前的决策点。另：回声消除已由例会确认由端侧负责，云侧不承担。
