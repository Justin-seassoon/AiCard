# 下周三功能 · 风险与待确认清单

> 状态：待产品 / 端侧拍板
> 日期：2026-10-10
> 背景：周报月报、主动推送、维修点检三功能已实现（六阶段完成，24 单测 + 集成测试全绿，打包通过）。以下 8 条为上线 / 联调前需对齐的风险点，按「报表口径 → 通知推送 → 配置流程」分组。

---

## 一、报表口径类（影响周报 / 月报准确性）

### 风险 1：存量 translation_sample 无法回填 device_id

- **现状**：`device_id` 列在 V14 才新增，此前采集的历史样本 `device_id` 为 NULL，且采集时本就没记录设备，无法可靠回填。
- **影响**：周报 / 月报只能从 V14 上线之日起按设备聚合，**历史翻译数据无法归属到具体员工**。
- **需拍板**：是否接受「报表从上线日起算，历史不追」？是否需要任何兜底（如按 session 推测，不推荐）。
- **建议**：接受从上线日起算，历史不追（技术回填不可靠）。

### 风险 2：报表口径是「样本近似」

- **现状**：`translation_sample` 是脱敏旁路样本（抽样），turn / 语种 / 活跃天数均为**抽样近似而非全量**；`session_id` 是连接级，跨重连的「会话数」语义与实际业务会话不一致。
- **影响**：报表数字是近似值，若用于**对客（SLA / 对账）**会产生口径争议。
- **需拍板**：报表定位是「内部运营参考」还是「对外对账」？「会话数」按连接级还是需重定义？
- **建议**：1.0 定位为内部运营参考，不对外承诺精确数字。

### 风险 3：时区与周期边界

- **现状**：周报周一 8 点、月报 1 号 8 点生成，按**单一服务器时区**。
- **影响**：若服务器时区 ≠ 日本 JST，周期切分点会错位。
- **需拍板**：服务器部署时区是否固定为 JST？1.0 是否需要按租户 / 门店时区？
- **建议**：1.0 固定服务器时区为 JST，后续再扩展多时区。

### 风险 4：员工姓名随设备当前值

- **现状**：`staff_name` 存在 device 表，换人时后台改字段，历史报表**不冻结当时的姓名**。
- **影响**：换人后，历史报表中显示的是「当前姓名」而非「当时姓名」。
- **需拍板**：是否接受？还是需要报表生成时快照姓名？
- **建议**：1.0 接受（实现简单），报表快照表已存 `device_id`，如需要可在生成时冗余姓名。

## 二、通知推送类（影响主动推送效果与成本）

### 风险 5：通知无已读回执

- **现状**：复用 `type="broadcast"` 通道（零端侧改动），只有「投递成功 / 补拉成功」两态，**无真实已读**。
- **影响**：无法确认员工是否真的看到通知。
- **需拍板**：1.0 是否需要已读回执？需要则端侧加 `notice_ack`（**单独立项**，需端侧配合）。
- **建议**：1.0 不做已读，仅投递回执。

### 风险 6：通知补拉 TTS 成本

- **现状**：离线设备重连后 `deliverPending` 会**重新合成 TTS** 补拉未投递通知。
- **影响**：大量离线设备集中补拉会产生 TTS 合成成本。
- **需拍板**：是否加「离线超时不再补拉」策略？超时阈值定多少（如 24h）？
- **建议**：加超时（建议 24h），需产品 / 端侧确认阈值。

## 三、配置与流程类

### 风险 7：system_config 覆盖粒度

- **现状**：调度配置支持**全局 / 租户 / 门店三级**覆盖（`UNIQUE(customer_id, store_id, config_key)`）。
- **影响**：三级已实现，但门店级覆盖若用不到，会带来配置维护复杂度。
- **需拍板**：保留三级，还是简化为「全局 + 租户」两级？
- **建议**：1.0 保留三级（已实现、无额外成本），确认用不到再后置收敛。

### 风险 8：维修点检设备关联

- **现状**：维修单 / 点检任务的 `device_id` 可空（未强制关联设备）。
- **影响**：是否允许「无设备」维修单？是否需要按门店批量派发点检？
- **需拍板**：字段放宽程度 —— 是否允许无设备？是否要批量派发？
- **建议**：1.0 允许 `device_id` 可空（已实现），批量派发后续再说。
