# 「主动与执行（远景）」落地可行性分析报告

> 日期：2026-09-20
> 范围：演示控制台「远」步所展示的全部 10 个「主动 → 执行 → 记忆」场景（连锁酒店 / 免税店 / 机场 / 工地 / 劳务派遣 / 制造 / 餐饮 / 农业 / 介护 / 清扫）
> 目的：评估每个场景在 **1.0 端侧硬件 + 现有云端架构** 约束下的真实落地难度，为「演示愿景」到「可交付功能」提供取舍依据。

---

## 一、结论先行（TL;DR）

1. **三种能力落地难度差异极大，不能混为一谈**：
   - **记忆（记住）**：纯云端数据存储，**现已具备**（postgres + 四层租户隔离），✅ 全部可行。
   - **执行（连系统办）**：分两类——「云端自有能力」（表单 / 工单 / 通知 / 台账 / 统计）✅ 1.0 就能做；「对接企业/第三方系统」（PMS / POS / GDS / 呼叫 / 税务）🔴 高门槛，1.0 大概率**降级为「生成工单转人工」**。
   - **主动（提前提醒）**：受**端侧「会话级短连接 + 7–10 天 Deep Sleep 待机」与「实时推送」的根本矛盾**制约，🟡 是最大卡点，需做架构取舍。

2. **核心矛盾（一句话）**：主动提醒要求设备「随时可被云端触达」，但 1.0 端侧为省电**待机时无长连接、无心跳**。所以「主动」要么只在设备在线时触发（窗口窄），要么让设备定时醒来轮询（牺牲待机），要么改硬件（1.0 板子无余量）。

3. **日本中小企业系统 API 普遍缺失**是「执行」的第二大卡点：PMS/POS/GDS 等封闭或收费，介护/考勤有成熟云服务但开放 API 的少。1.0 落地应把「执行」聚焦在**云端自有台账/工单/通知**，对接外部系统一律延后。

---

## 二、评估口径（统一框架）

### 2.1 三能力评级定义

| 评级 | 含义 | 判断标准 |
|---|---|---|
| ✅ 可行 | 现有架构/硬件即可实现，无需新基建 | 纯云端存储、云端自有流程、已有推送通道（在线时） |
| 🟡 有条件可行 | 需降级、或需端侧/商务配合、或有明显取舍 | 实时推送→轮询；对接系统→转人工；需端侧加定时唤醒 |
| 🔴 高门槛 | 1.0 大概率做不了，需外部 API/商务/硬件改造 | PMS/POS/GDS/呼叫/税务对接；长连接/常开唤醒 |

### 2.2 端侧硬件现实（交互可行性的基础）

来自 PRD §7 与已冻结协议：

| 硬件能力 | 现状 | 对「主动提醒」的影响 |
|---|---|---|
| 显示 | **彩屏**，无触屏，有方向键+确认键 | 可显示短文字/图标/菜单，支持菜单式交互；复杂多语言受本地字体库限制 |
| 播报 | **扬声器 TTS 外放**（设备只播 TTS、不显示翻译文本） | 主动提醒最自然载体，但**打扰性强**（客人面前、安静环境） |
| 提示 | LED 指示灯 | 只能表达「有消息」，无法传内容，需配合按键拉取 |
| 输入 | 翻译键 + 高频语言键 + 方向键 + 确认键（无触屏） | 可通过方向键+确认键做菜单式交互（查看任务/稍后提醒/确认完成）；长文本仍需后端/App |
| 采集 | 4 麦阵列 + VAD（静音 1.2s 断句）+ AEC | 与提醒无关 |
| 功耗 | 待机 7–10 天（Deep Sleep），1500mAh | **硬约束**：不能常开长连接/心跳 |
| 通信 | 双频 Wi-Fi（可选 4G Cat.1）；**会话级短连接**，睡眠前上报 sleep_notice | 待机时云端**无法触达设备** |

### 2.3 「主动推送」的三种技术路径（关键取舍）

| 路径 | 机制 | 实时性 | 功耗代价 | 可行性 |
|---|---|---|---|---|
| A. 在线触发 | 设备在会话中 / 刚按键唤醒后，云端即时下发 | 实时（0 延迟） | 无额外代价 | ✅ 立即可做，但**窗口窄**（员工大部分时间待机） |
| B. 定时轮询 | 设备每 N 分钟醒来，Wi-Fi 连一次查待办再睡 | 延迟 ≈ N/2~N 分钟 | 每次唤醒 1–2s 连接 + HTTP；N 越小越耗电 | 🟡 需端侧固件配合，与 7–10 天待机 trade-off |
| C. 常开低功耗心跳 | BLE/低频保活，云端实时触达 | 实时 | 需 BLE 常开/网关 | 🔴 1.0 板子无余量（BLE 仅预留配网） |

> **判断**：1.0「主动提醒」的现实形态是 **A 为主（在线时即时推送）+ B 折中（离线补拉，复用广播的「准实时 + 离线补拉」模型）**。真正的「实时主动触达」是 1.0 之后的硬件/协议议题。

## 三、10 个场景逐项分析

> 每项按「需接入的数据 → 交互链路（端侧）→ 三能力评级 → 1.0 落地建议」展开。

### 3.1 连锁酒店 —— VIP 到店提醒 / 叫车·查空房·写工单 / 记住偏好

- **需接入的数据**
  | 数据 | 来源 | 难度 |
  |---|---|---|
  | 客户订单、到店时间、房型 | PMS（楽天トラベル連携 / 手間いらず / NEHO 等） | 🔴 高（API 封闭/收费，小旅館用 Excel） |
  | 偏好标签（高层/安静/过敏） | 云端自有 + 前台手工录入 | ✅ 低 |
  | 叫车 / 查空房 | 打车 API（GO / S.RIDE）/ PMS | 🔴 高 |
- **交互链路**：VIP 到店事件 → 云端判断前台工牌是否在线 → 在线则 TTS 提醒「王先生 14:00 到店，偏好高楼层」；离线则入待办，下次在线补推 → 前台按键确认。
- **评级**：主动 🟡（只能在线时到）/ 执行 🟡（叫车/查房需 PMS，可降级为生成工单）/ 记忆 ✅
- **1.0 建议**：**记忆全做**；「写投诉工单」做云端自有工单 ✅；「叫车/查空房」**降级为「生成工单转前台人工」**；「VIP 到店提醒」仅在设备在线时触发。

### 3.2 免税店 —— 龙角散补货提醒 / 查库存·开退税单·记客诉 / 记住购买历史

- **需接入的数据**
  | 数据 | 来源 | 难度 |
  |---|---|---|
  | 库存 / 销量 | POS / 库存系统 | 🔴 高 |
  | 免税手续 | 国税厅「免税销售信息电子化」/ POS | 🔴 高（管制） |
  | 会员画像（皮肤类型/品牌偏好） | 云端自有 + 柜员录入 | ✅ 低 |
- **交互链路**：库存低于阈值 → 在线则 TTS 提醒柜员补货 + 推话术；离线补推 → 柜员按键确认。
- **评级**：主动 🟡 / 执行 🟡（开退税单🔴）/ 记忆 ✅
- **1.0 建议**：会员画像、客诉记录（云端自有）✅；「查库存/开退税单」降级为工单；「补货提醒」仅在线触发，或先做「柜员主动问『龙角散还有吗』→ 工牌从云端库存答」的**拉取式**替代。

### 3.3 机场 —— 登机口变更·误机预警 / 改签·查航班·叫车 / 记住常旅客偏好

- **需接入的数据**
  | 数据 | 来源 | 难度 |
  |---|---|---|
  | 航班/登机口动态 | AODB / 登机口系统 / FlightStats 类 | 🔴 高（管制，需机场授权） |
  | 改签 | GDS（Amadeus/Sabre） | 🔴 高（航司系统，几乎不可行） |
  | 常旅客偏好 / 轮椅需求 | 云端自有 + 地勤录入 | ✅ 低 |
- **交互链路**：登机口变更 → 在线则 TTS 提醒地勤 + 推送旅客母语通知；离线补推。
- **评级**：主动 🟡 / 执行 🔴（改签几乎不可行）/ 记忆 ✅
- **1.0 建议**：**机场场景 1.0 主做「翻译 + 知识库」，主动与执行基本延后**。唯一可做的是「登机口变更」这类**机场方已有广播/通知源** → 工牌转发母语通知（复用分组广播），但需机场数据授权。

### 3.4 工地 —— 台风停工提醒 / 报工伤·派工·统计到岗 / 记住技能·资质·在留期限

- **需接入的数据**
  | 数据 | 来源 | 难度 |
  |---|---|---|
  | 天气预警 | 気象庁 API / 商业天气（Weathernews 等） | ✅ 低（最可行） |
  | 考勤 | 云考勤（KING OF TIME 等）或手工白板 | 🟡 中（有 API 但需对接；小工地手工） |
  | 劳工技能/资质/在留 | 云端自有 + 派遣方录入 | ✅ 低 |
- **交互链路**：气象厅台风预警 → 云端广播「停工」→ 各劳工母语 TTS（复用分组广播，准实时 + 离线补拉）→ 到岗统计靠按键回执。
- **评级**：主动 🟡（天气预警有明确触发源，最接近可实现）/ 执行 🟡（报工伤做云端表单 ✅，考勤对接降级）/ 记忆 ✅
- **1.0 建议**：**工地是「主动」最值得先做的场景**——天气预警源免费、广播通道已上线、安全价值最高。「报工伤/派工/统计」做云端自有表单 ✅。

### 3.5 劳务派遣（管理方）—— 在留续签提醒 / 排班派工·发通知·统计考勤 / 记住技能·考勤·考评

- **需接入的数据**
  | 数据 | 来源 | 难度 |
  |---|---|---|
  | 在留期限 | 人工录入（入管数据非公开） | ✅ 低（但需人工维护） |
  | 考勤/考评 | 派遣公司系统（SmartHR / KING OF TIME 类） | 🟡 中 |
  | 技能/培训进度 | 云端自有 | ✅ 低 |
- **交互链路**：在留期限提前 N 天 → 云端给管理员（而非劳工）提醒；排班/停工 → 分组广播给劳工母语。
- **评级**：主动 🟡（提醒对象是「管理员」，可用 App/后台看板而非工牌，反而绕开端侧待机矛盾）/ 执行 🟡 / 记忆 ✅
- **1.0 建议**：**管理方的「主动提醒」可以不走工牌**，用运营后台/App 推送即可，可行性反而更高；给劳工的派工/停工走分组广播 ✅。

### 3.6 制造 —— 设备点检·不良率预警 / 报不良·维修工单·排班 / 记住技能等级

- **需接入的数据**
  | 数据 | 来源 | 难度 |
  |---|---|---|
  | 设备点检计划 / 不良率 | MES / QMS（大厂有，小厂手工） | 🟡 中–🔴 高 |
  | 维修工单 | 云端自有 | ✅ 低 |
  | 劳工技能等级 | 云端自有 | ✅ 低 |
- **评级**：主动 🟡（点检是「定时任务」，可用轮询/日历推送）/ 执行 🟡（报不良/维修工单做云端自有 ✅）/ 记忆 ✅
- **1.0 建议**：点检提醒可做成「排班表 + 在线时 TTS 提醒」；不良品上报、维修工单做云端自有表单 ✅；对接 MES 延后。

### 3.7 餐饮 —— 卫生检查·诺如预警 / 报食安·补货·排班 / 记住卫生记录

- **需接入的数据**
  | 数据 | 来源 | 难度 |
  |---|---|---|
  | 卫生检查 / 诺如预警 | 厚労省/保健所通告、内部检查表（纸/Excel） | 🟡 中（多为手动，无 API） |
  | 补货 | POS / 进货系统 | 🔴 高 |
  | 卫生记录 / 培训进度 | 云端自有 | ✅ 低 |
- **评级**：主动 🟡（诺如/卫生检查是周期性的，可定时提醒）/ 执行 🟡（报食安做表单 ✅）/ 记忆 ✅
- **1.0 建议**：卫生检查清单、诺如高发期提醒做成「定时 + 在线提醒」；食品安全上报做云端表单 ✅；补货对接 POS 延后。

### 3.8 农业 —— 农药安全间隔·高温预警 / 记农药台账·报天气·派工 / 记住农田·农药记录

- **需接入的数据**
  | 数据 | 来源 | 难度 |
  |---|---|---|
  | 天气/高温预警 | 気象庁 API | ✅ 低 |
  | 农药安全间隔 | 云端规则 + 台账录入 | ✅ 低（GAP 合规台账） |
  | 农药使用台账 | 农协系统或手工 | 🟡 中 |
- **评级**：主动 🟡（天气预警源免费，接近可实现）/ 执行 ✅（记农药台账是云端自有，且 GAP 合规刚需）/ 记忆 ✅
- **1.0 建议**：与工地类似，**农业的「主动」也值得先做**（天气预警免费 + 台账刚需）。农药台账做成云端自有 ✅。

### 3.9 介护 —— 翻身服药·褥疮预警 / 呼叫支援·护理日志·通知家属 / 记住病史·护理计划

- **需接入的数据**
  | 数据 | 来源 | 难度 |
  |---|---|---|
  | 护理计划/翻身服药时刻 | 介护记录软件（CAREBOOK / ほのぼのNEXT 等） | 🟡 中（软件成熟，开放 API 少） |
  | 呼叫支援 | 护士呼叫系统 | 🔴 高 |
  | 病史/偏好 | 云端自有（⚠️「要配慮個人情報」，合规更严） | ✅ 低（但合规重） |
- **评级**：主动 🟡（翻身/服药是**定时**的，天然适合提醒，介护是主动提醒最刚需场景）/ 执行 🟡（护理日志做云端自有 ✅；呼叫系统对接 🔴，降级为发消息给组长）/ 记忆 ✅（但医疗数据合规重）
- **1.0 建议**：**介护的「定时翻身/服药提醒」是主动提醒最高价值、最清晰触发源的场景**，优先做；护理日志云端自有 ✅；呼叫系统 1.0 降级为「工牌发消息给当班组长」。

### 3.10 清扫 —— 检查临近·化学品预警 / 报失物·派区域·记检查 / 记住负责区域

- **需接入的数据**
  | 数据 | 来源 | 难度 |
  |---|---|---|
  | 检查计划 | 清扫公司系统 / 手工 | 🟡 中 |
  | 失物 | 酒店 PMS 联动 | 🔴 高 |
  | 负责区域 / 检查结果 | 云端自有 | ✅ 低 |
- **评级**：主动 🟡（检查临近是周期性的，可定时提醒）/ 执行 🟡（报失物做云端表单 ✅）/ 记忆 ✅
- **1.0 建议**：检查计划提醒做成「定时 + 在线提醒」；失物上报做云端表单 ✅；对接酒店 PMS 延后。

## 四、跨场景共性结论

### 4.1 数据接入是「执行」的普遍卡点

10 个场景里，「连系统办」的多数动作（查空房/开退税单/改签/呼叫支援/补货/失物）**都依赖一个封闭或管制的外部系统**。日本中小企业普遍无开放 API，所以：

> **1.0 落地的正确姿势**：把「执行」聚焦在**云端自有能力**（表单、工单、通知、台账、统计、回执）——这些不依赖任何外部系统，现在就能做；「对接企业系统」一律标注为 P2（需商务 + API），并用「生成工单转人工」兜底。

### 4.2 「主动提醒」在端侧的现实形态

- **最可行**：有**明确、免费触发源**的场景——工地/农业的天气预警、介护的定时翻身服药、制造/清扫的定时点检检查。这些要么是「定时任务」，要么有免费 API。
- **绕开矛盾**：提醒对象是**管理方**的场景（劳务派遣的在留续签），可用后台/App 推送，不必占用端侧实时通道。
- **必须端侧配合**：真正的「实时主动触达」需要端侧支持定时轮询唤醒（路径 B），或未来硬件加低功耗保活（路径 C）。这是与 7–10 天待机的量化 trade-off，需端侧共同拍板。

### 4.3 交互友好性（基于现有硬件）的关键判断

| 提醒类型 | 呈现方式 | 友好性 | 备注 |
|---|---|---|---|
| 短指令（停工/补货/翻身） | TTS 外放 1 句话 | 🟡 中 | 最直接，但打扰；建议「LED 提示 → 员工按键 → 才播 TTS」的**拉取式**更礼貌 |
| 待办/清单 | 彩屏菜单 + LED | 🟡 中 | 彩屏可显示待办菜单，方向键浏览；但员工未必低头看 |
| 长内容/表单 | 均不适合 | 🔴 | 无触屏、无键盘，长表单必须走后端/App |

> **建议**：主动提醒默认走 **「LED 亮 + 彩屏图标/菜单 → 员工方向键选择或按键 → TTS 播报内容 → 确认键回执」** 的链路，避免在客人面前突然外放（尤其酒店/免税/介护等礼貌敏感场景）。这要求端侧支持「提醒队列 + 按键拉取播报」，属端侧配合项。

## 五、1.0 落地优先级建议（Roadmap）

| 优先级 | 内容 | 说明 |
|---|---|---|
| **P0（现在就能做，无需新基建）** | ① 全部「记忆」能力；②「执行」的云端自有部分（表单/工单/通知/台账/统计/回执）；③「主动」的**在线时触发**（复用现有 WSS + 广播通道） | 纯云端 + 已有通道 |
| **P1（需端侧固件配合）** | ④ 定时轮询唤醒（路径 B，折中功耗）；⑤ 彩屏待办菜单 + 方向键/按键拉取播报 | 需端侧拍板「功耗 vs 实时」量化指标 |
| **P2（需商务 + API）** | ⑥ 对接企业系统（PMS/POS/GDS/呼叫/免税/介护软件）；⑦ 天气/交通等免费第三方 API 接入 | 逐家谈商务，1.0 后用「工单转人工」兜底 |
| **P3（需硬件改造）** | ⑧ 低功耗保活心跳（路径 C） | 1.0 板子无余量，V2 评估 |

## 六、风险与开放问题

1. **功耗 vs 实时性的量化**：若走「定时轮询」，N 取多少？需端侧实测「每次唤醒耗电」与「7–10 天待机」的关系，给出「N=5min 待机缩到 X 天」的曲线，才能拍板。
2. **打扰与礼仪合规**：日本服务业在客人面前外放提醒可能泄露客人信息、不礼貌。需设计「静默提示 + 按键拉取」的默认交互，并允许员工关闭语音。
3. **隐私合规**：采集客人偏好、介护病史（属「要配慮個人情報」）、劳工数据，需满足日本《个人情报保护法（APPI）》的同意取得 + 安全管理措施 + 数据最小化。
4. **数据来源真实性**：1.0 大量数据靠「人肉录入/Excel 导入」，存在「录入滞后 → 提醒失真」的风险，需在演示与真实部署中明确区分。
5. **提醒触达窗口窄**：路径 A（在线触发）下，员工大部分时间待机，提醒大概率「延迟到下次按键才送达」，需向演示/客户如实说明这是「准实时」而非「秒级实时」。
