AI 工牌 1.0 · 分组多语言广播能力设想
通用云端能力 + 行业示例 · 2026-09-13 · 纸面预研（暂不涉及代码）

一、定位：从「建群管理」到「通用广播能力」

  • 原需求「建群管理」（工地多国劳工建群广播）抽掉行业外壳，本质是「分组多语言广播」。
  • 四个要素——分组、广播、语言路由、回执——无一绑定「建筑」，天然是通用中台能力。
  • 定位为与「一对一对话」并列的第二产品支柱，而非某个行业的竖井功能。

二、四个核心要素

  • 分组 Group：一组设备的集合，可嵌套（工地 → 班组）。
  • 广播 Broadcast：一条源消息 → 按成员语言分别翻译 → 批量下发。
  • 语言路由：每台设备一个目标语言（复用一机一码已登记的默认语言对）。
  • 回执 Ack：成员确认状态回流 + 汇总看板。

三、可复用行业（举例）

  • 工厂 / 制造业：多语种产线工人的安全通知、班次调度。
  • 酒店 / 服务业：多语种员工班前会、VIP 到店、突发事件广播。
  • 机场 / 交通枢纽：多语种地勤 / 安保的航班变更、紧急广播。
  • 展会 / 大型活动：多语种工作人员现场统一调度。
  • 医院 / 护理：多语种护工医嘱传达、紧急呼叫。
  • 物流 / 仓储：多语种工人任务分配。
  • 共同点：任何「有多语种成员、需统一触达 + 回收确认」的团队场景。

四、与「一对一对话」的关系

  • 一对一对话 = 个人沟通（店员 ↔ 游客）；分组广播 = 组织沟通（管理员 → 全员）。
  • 两者是并列的两个支柱、不是从属；云端应做成并列的通用服务。

五、对云端的新增要求（通用能力）

  • 分组管理：group 实体 + 可嵌套 + 成员关系（复用四层租户隔离，加 group_id）。
  • 广播编排：源消息 → N 翻译 → N TTS → N 推送（复用 MT / TTS 供应商抽象）。
  • 下行推送通道：云端主动下行（现有是设备按需短连接），最大架构差异点。
  • 确认回执：ack 上报 + 汇总看板。
  • 后台 UI：分组管理 + 广播记录 + 回执看板（复用 RBAC）。
  • 行业模板：工地 / 酒店等差异做成配置 / 模板，不做每行业一个功能。

六、与现有架构的复用与差异

  • 关键复用：一机一码已登记每设备的「默认语言对」＝ 广播所需的「成员语言画像」，无需新发明语言归属。
  • 复用：设备鉴权、MT / TTS 多供应商抽象、四层租户隔离、RBAC、旁路采集。
  • 差异（见下表）：
维度现有：一对一对话新增：分组广播
会话模型设备按需建立会话级短连接云端主动下行推送（需常连接 / 推送机制）
翻译方向对话双向轮流单向一对多（源 → N 母语）
触发方式按键触发管理员后台触发
消息形态语音对话（不显示文本）文本 + 语音播报 + 墨水屏显示
回执无按键确认回执

七、需预研讨论的问题

  • 下行通道选型与功耗：WSS 常连接 / MQTT / 端侧轮询？对「7–10 天待机」的影响。
  • 消息形态：文本优先还是语音？工地噪声对 TTS 播报可靠性的影响；墨水屏是否够显示。
  • 确认粒度：整条确认，还是带选项（收到 / 有疑问）？
  • 群规模与成本：单群工牌数上限？批量翻译 + TTS 的成本模型。
  • 权限：谁能发广播（管理员 / 班组长）？
  • 模式切换：工牌上如何区分「群广播」与「对话翻译」？
  • 离线补发：设备错过广播怎么办（重连补发 / 去重）？
  • 行业模板抽象粒度：哪些字段可变、哪些固定，避免做成每行业一套。
