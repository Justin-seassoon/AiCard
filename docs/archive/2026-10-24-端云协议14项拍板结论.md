## 二、已定口径（12 项）

### 1. 会议录音走 HTTP

- 开始 / 分片 / 结束 / 状态全部走 HTTPS REST；会议期间不维持 WSS。
- 理由：会议可能持续 30–120 分钟，长连接功耗和重连成本高；分片上传天然适合 HTTP，失败只重传一片。
- 端侧要做：HTTPS 客户端、TLS、keep-alive、指数退避重试。

### 2. 分片 5–30 秒，端侧按 PSRAM 选

- 端侧在 5/10/15/20/30 秒中选择，`start` 时传入；**60 / 120 秒不支持**（PSRAM 无法缓存 60 秒双片；120 秒还超过 2MB 传输上限）。
- 30 秒 PCM16/16k 约 960KB；1–2 片缓存约 1–2MB；5–10 分钟需 9.6–19.2MB，超出 PSRAM 预算。
- 端侧要做：按可用 PSRAM 在 5/10/15/20/30 秒中选择，`start` 时传入；只缓存 1–2 片，不做长时间离线缓存。

### 3. `last_seq` 必填

- 设备结束会议时必须告诉云端「最后录到第几片」。
- 否则末尾丢片无法发现：例如只传到 97、实际录到 100，云端会认为 97 就是最后一片，转写静默截断。
- 端侧要做：持久化 `last_seq`（NVS / 文件），重启后能读到。

### 4. `end` 返回缺片列表

- `end` 返回 `missing_seqs`、`expected_last_seq`、`uploaded_count`，不只返回数量。
- 端侧要做：按 `missing_seqs` 升序补传。

### 5. 增加状态 / 续传接口

- 增加 `GET /api/v1/meetings/{id}`：返回状态、已收到序号、缺片、到期时间、错误信息。
- `start` 用 `client_key` 幂等：设备重启后拿同一个 key 再 `start`，返回原会议。
- 端侧要做：本地保存 `meeting_id` + `client_key`；启动时先查状态再决定续传或重开。

### 6. v1 只支持 PCM16

- PCM16 / 16kHz / 单声道；与 WSS 音频、WAV 导入一致。
- 代价：1 小时约 115MB；Opus 放 v1.1，等设备确认编码能力与云端解码方案。
- 端侧要做：确认目标网络下 115MB/小时可接受；如果 4G 场景必须 Opus，提前提出。

### 7. HTTP 鉴权统一 Bearer

- 统一 `Authorization: Bearer <device_token>` + `X-Device-Id`；与 OTA 一致。
- **开发阶段不做旧 `X-Device-Token` 兼容**，所有固件统一按新格式实现。
- 端侧要做：HTTP 栈加 Bearer；token 刷新流程与 OTA 共用。
- 备注：如果 token 刷新流程还没定，开发 / demo 可继续用静态 token，但格式按 Bearer。

### 8. 增加 `features`

- `session_init.features`（设备 → 云）与 `config_update.features`（云 → 设备）；会议 `start` 也带 `features`。
- 生效 = 设备支持 ∩ 云端开启；**新固件必须上报，不做「不传 = 不支持」的旧固件回退**。
- 端侧要做：维护能力列表（如 `meeting_recording`、`notice_ack`）；收到不认识的 feature 忽略。

### 9. 云端强制最低固件版本

- `start` 请求带 `fw_version`；云端校验 `features` 包含 `meeting_recording` + `fw_version ≥ 最低版本`。
- 开发阶段所有设备统一升到首个支持版本，不存在旧设备兼容。
- 端侧要做：提供首个支持会议录音的 P4 / C5 版本号；请求带版本。

### 12. 通知 / 待办 / 报表已读回执（v1.1）

- 新增通用 `notice` + `notice_ack`，不继续给 `broadcast` 加语义。
- `notice_type`：`operation` / `action_reminder` / `report_ready`；`requires_ack` 控制是否等确认。
- 不阻塞会议 v1；等会议稳定后再做。
- 端侧要做（v1.1）：通知显示 / 播放 + OK 键回执；「已读」与「任务完成」分开。

### 13. OTA 中间组合：1.0 不做

- 开发阶段没有旧版本，所有设备从统一基线开始；发布时保证任意支持版本可直达目标。
- OTA 冻结稿里的「起始组合 → 中间组合 → 目标组合」迁移表 1.0 不实现。
- 端侧要做：确认 P4 / C5 不存在「必须先升中间版本」的依赖；如果有，提前提出。

### 14. 缺片补传：`end` 保持可补状态

- `end` 有缺片 → 状态保持 `uploading`，返回 `missing_seqs`；设备补片后**再次调用 `end`**；缺片为空时转写。
- 设备崩溃 / 不再调用 → 沿用现有「10 分钟无新分片自动转写」兜底。
- 不新增 `finalize` 接口；不再用 60 秒硬窗口。
- 端侧要做：接受「补片后再调一次 `end`」；补片期间不继续录音。

## 四、待产品 / 合规确认（2 项）

### 10. 现场提示话术 / 触发

- 技术方案已定：长按开始 → 本地提示（提示音 + LED / 屏幕）→ `start` 带 `trigger: long_press`、`notice_played: true`、`notice_version`；云端留痕；**不提供远程静默开启**。
- 待确认：
  - 提示话术文本（是否需要多语言）
  - 是否要求二次按键确认后才开始录音
  - 审计字段保留多久

### 11. 取消会议是否删除音频

- 技术方案已定：`POST /abort` → 立即删除分片 / 转写 / 纪要 → 保留最小审计元数据（`meeting_id`、设备、起止时间、取消人、原因、取消时间）。
- 待确认：
  - 审计元数据保留多久
  - 已转写 / 已审核的会议是否允许取消（建议不允许，走单独删除流程）
  - 取消操作方式（长按 / 组合键）

## 五、明确不做

| 不做项 | 原因 |
|---|---|
| 旧 `X-Device-Token` 兼容 | 开发阶段无旧固件，统一 Bearer |
| 旧固件不传 `features` 的回退分支 | 统一要求新固件上报 |
| OTA 中间组合迁移表（1.0） | 无旧版本，统一基线直达 |
| 会议走 WSS | 长连接功耗 / 重连成本高 |
| Opus / ADPCM（v1） | 转写链路未支持；v1.1 再评估 |

## 六、给端侧的一页版（可直接转发）

> 会议录音 v1 我方口径已定，请确认实施项。

**协议结论**：

1. 会议走 HTTPS：`start / 分片 / end / status`，不维持 WSS。
2. 端侧按 PSRAM 在 5–30 秒中选择分片（优先 15；预算 ≥2MB 可用 30），PCM16 / 16kHz / 单声道。
3. `start` 用 `client_key` 幂等；请求带 `fw_version`、`features`。
4. `end` 必须带 `last_seq`；返回 `missing_seqs`。
5. `end` 有缺片时保持 `uploading`，补片后再次调用 `end`；10 分钟无新片自动转写。
6. 增加 `GET /meetings/{id}` 状态查询。
7. HTTP 鉴权统一 `Authorization: Bearer` + `X-Device-Id`，不做旧头兼容。
8. 1.0 不做 OTA 中间组合。
9. 通知已读回执放 v1.1，不阻塞会议。

**请端侧确认 / 提供**：

- HTTPS 栈、keep-alive、token 刷新流程
- 可用于录音缓冲的 PSRAM 上限与建议分片（5/10/15/20/30 秒）
- 能否持久化 `last_seq` / `meeting_id` / `client_key`
- `features` 能力列表
- 首个支持会议录音的 P4 / C5 版本号
- 补片后再调 `end` 是否可行
- P4 / C5 是否存在必须先升中间版本的依赖

**待产品 / 合规**：现场提示话术、是否二次确认、取消后审计保留范围。
