# 端云协议对齐与迭代梳理

> 日期：2026-10-24
> 范围：WSS 会话协议、OTA 协议、会议录音 HTTP 接口，以及通知 / 报表 / 任务 / 知识反馈等后续场景
> 目的：先统一「现在有什么、哪些已冻结、会议录音要补什么、OTA 要不要动」，作为端云两侧对齐会的输入。
> 📌 **协议基线已合并到《[端云通信协议-唯一基线](../baseline/端云通信协议-唯一基线.md)》；拍板结论见《[端云协议 14 项拍板结论与端侧确认清单](2026-10-24-端云协议14项拍板结论.md)》；本文件保留为差距分析与建议来源。**
> 依据：`docs/archive/端云通信接口规范-v1.md`、`docs/archive/2026-09-22-OTA协议确认-端云冻结版.md`、`docs/通信协议联调说明.md`、会议录音设备接口代码。

## 0. 结论先行

1. **WSS 会话协议 v1 已冻结，不建议为会议录音改动它**；会议录音走独立的 HTTP 接口更合适（30 秒分片、断网续传、不依赖长连接）。
2. **会议录音目前只有代码，没有协议文档**。P0 的 `start / chunk / end` 已可用，但缺「状态查询、缺片清单、断点续传、错误码、鉴权统一」等设备落地必需项。
3. **OTA 协议本身不需要改**；会议录音需要新固件，OTA 负责把固件发下去。需要补的是「固件版本 / 协议版本 / 功能开关」的协商，建议放在 `session_init` 与 `config_update`，不要塞进 OTA 接口。
4. **端云两侧现在有三套鉴权和三种错误格式**：WSS 用 query 参数、OTA 用 Bearer、会议用 `X-Device-Id + X-Device-Token`；错误格式也不一致。建议统一 HTTP 侧为 Bearer + `X-Device-Id`，并统一错误信封。
5. **协议文档的版本号是乱的**：文件名 `v1`、内容写 `v4` 并包含 `v5` 修订、握手 `proto_ver=1`。需要区分「协议版本」与「文档修订」，并建立一份协议索引与变更流程。
6. **建议先做三件事**：
   - 冻结《会议录音 HTTP 接口 v1》文档（补状态、缺片、错误码、鉴权）
   - 在 WSS v1.1 增加可选 `features` / 配置项（向后兼容）
   - 建立协议索引与变更评审流程，OTA 文档只补「新固件与功能开关」说明

## 2. 当前已冻结的基线（速查）

### 2.1 WSS 会话协议 v1

- 传输：WSS；音频二进制帧，控制 JSON 文本帧。
- 握手：`device_id` / `token` / `fw_version` / `proto_ver` 走 query。
- 上行：`session_init`、`0x01` 音频帧、`eou`、`stop_tts`、`sleep_notice`、`button_event`、`playback_event`、`scope_change`、`translation_mode_change`、`headset_event`、`config_pull`、`broadcast_ack`。
- 下行：`0x81` TTS 帧、`tts_end`、`error`、`final_text` / `partial_text`、`answer`、`language_state`、`config_update`、`output_route`、`broadcast`。
- 错误：`{type:"error", code, message, fallback_action}`。
- 参数：16kHz / PCM16 / 100ms 上行帧 / 8KB 单帧 / 10s 心跳 / 20s 空闲超时。

### 2.2 OTA 协议 v1

- 通道：独立 HTTPS，不走 WSS。
- 检查：`POST /api/v1/ota/check`，Bearer token，上报 P4/C5 版本，返回固定配套目标与有序包清单。
- 下载：短期签名 URL，`application/octet-stream`，校验长度与 SHA-256。
- 结果感知：1.0 不做进度/结果上报，下次 `check` 的 `current_versions` 被动感知。
- 错误：`{error_code, message}` + HTTP 状态码。

### 2.3 会议录音 P0（已实现，未成文）

| 接口 | 作用 | 现状 |
|---|---|---|
| `POST /api/meetings/start` | 开始会议，返回 `meeting_id`、分片地址、分片时长、音频到期时间 | 支持 `client_key` 幂等；`started_at` 会做时钟校正 |
| `PUT /api/meetings/{id}/chunks/{seq}` | 上传分片，`application/octet-stream`，可选 `X-Chunk-Sha256` | 幂等；同序号不同内容返回 409；单片上限 2MB |
| `POST /api/meetings/{id}/end` | 结束并触发转写 | `last_seq` 可选；返回 `missing_count`，**不返回缺片列表** |

- 鉴权：`X-Device-Id` + `X-Device-Token`。
- 音频：PCM16、16kHz、单声道；分片默认 30 秒。
- 处理：异步转写 → 结构化纪要 → 待办；后台可编辑、审核、导出 Word。
- 兜底：10 分钟无新分片自动结束；音频 30 天到期删除。

## 3. 会议录音：协议要补什么

### 3.1 设备落地的完整流程

```
长按开始
  → 本地提示（提示音 / 指示灯 / 屏幕「录音开始」）
  → POST start（client_key 幂等）
  → 每 30 秒录音分片
  → PUT chunk（seq + sha256，失败重试）
  → 长按结束
  → POST end（last_seq 必填）
  → 返回缺片列表 → 补传
  → 设备显示「上传完成 / 转写中」
  → 可选：云端通知「纪要已生成」
```

### 3.2 当前缺口

| 缺口 | 现状 | 影响 |
|---|---|---|
| 协议文档 | 只有代码注释 | ODM 无法按文档实现 |
| `last_seq` 必填 | 可选；不传时只按已收到的最大序号判断 | 设备末尾丢片时，云端发现不了 |
| 缺片列表 | `end` 只返回 `missing_count` | 设备不知道补哪几片 |
| 状态查询 | 设备侧没有 `GET status` | 重启 / 断网后无法续传 |
| 续传 | 只有 `start` 的 `client_key` 幂等 | 没有「我传到第几片、还缺哪些」的接口 |
| 鉴权 | `X-Device-Id + X-Device-Token` | 与 OTA 的 Bearer 不一致 |
| 错误码 | Spring 默认错误 | 设备无法按错误类型重试 |
| 音频格式 | 字段接受 `pcm16 / opus / adpcm` | 转写链路只按 PCM16 处理，需冻结或补解码 |
| 提示与知情 | 协议没有 | 合规要求「开始录音有现场提示」 |
| 状态反馈 | 无 | 设备不知道转写 / 纪要是否完成 |
| 多会议 | 未定义 | 同一设备并发开会话的行为不明确 |

### 3.3 建议的会议 HTTP 接口 v1

> 建议统一加 `/api/v1` 前缀；后台接口可以继续用 `/api/...`，设备接口单独版本化。

#### ① 开始 `POST /api/v1/meetings`

请求：

| 字段 | 必填 | 说明 |
|---|---|---|
| `client_key` | 是 | 设备生成的幂等键；重试用同一个 |
| `started_at` | 否 | 设备本地时间；云端会校正 |
| `codec` | 否 | v1 固定 `pcm16`（Opus 后续再开） |
| `sample_rate` | 否 | v1 固定 `16000` |
| `chunk_sec` | 否 | 默认 30，允许 5–120 |
| `title` | 否 | 会议标题 |

响应：

| 字段 | 说明 |
|---|---|
| `meeting_id` | 会议 ID |
| `status` | `recording` |
| `chunk_sec` | 实际分片时长 |
| `max_chunk_bytes` | 单片上限（当前 2MB） |
| `retention_days` | 音频保留天数（当前 30） |
| `chunk_url` | 分片地址模板 |
| `audio_expires_at` | 音频到期时间 |

#### ② 上传分片 `PUT /api/v1/meetings/{id}/chunks/{seq}`

- `Content-Type: application/octet-stream`
- `X-Chunk-Sha256`：建议必填（或由云端计算并返回）
- 成功 `204`；重复上传同内容幂等；同序号不同内容 `409`
- 超过 `max_chunk_bytes` → `413`
- 会议已结束 / 已过期 → `409 / 410`

#### ③ 结束 `POST /api/v1/meetings/{id}/end`

请求：`{ "last_seq": 123 }`（**必填**）

响应：

```json
{
  "meeting_id": "mtg-...",
  "status": "transcribing",
  "expected_last_seq": 123,
  "missing_seqs": [7, 8],
  "duration_sec": 3720
}
```

- `missing_seqs` 为空才代表完整；设备按列表补传，补传后再次 `end`（幂等）。
- 若设备不传 `last_seq`，云端按已收到的最大序号处理，**无法发现末尾丢片**，所以协议层应必填。

#### ④ 状态查询 `GET /api/v1/meetings/{id}`

返回：`status`、`last_seq`、`expected_last_seq`、`missing_seqs`、`uploaded_count`、`audio_expires_at`、`error_message`。

用途：设备重启、断网重连、上传失败后恢复。

#### ⑤ 取消 `POST /api/v1/meetings/{id}/abort`（可选）

用于用户取消、录音作废；是否删除已上传音频需产品确认。

#### ⑥ 统一错误信封

```json
{ "error_code": "E_MEETING_SEQ_CONFLICT", "message": "chunk exists with different content", "retryable": false }
```

建议错误码：

| 错误码 | 场景 | 设备行为 |
|---|---|---|
| `E_MEETING_AUTH` | 鉴权失败 | 重新取 token，不重试上传 |
| `E_MEETING_NOT_FOUND` | 会议不存在 / 不属于该设备 | 停止，提示 |
| `E_MEETING_STATE` | 已结束 / 不接受分片 | 查状态后决定 |
| `E_MEETING_EXPIRED` | 音频已过期 | 停止，提示 |
| `E_MEETING_TOO_LARGE` | 单片超限 | 减小分片后重传 |
| `E_MEETING_SEQ_CONFLICT` | 同序号不同内容 | 停止该片，人工确认 |
| `E_MEETING_SHA_MISMATCH` | 校验失败 | 重传该片 |
| `E_MEETING_RATE_LIMIT` | 限流 | 退避重试 |

### 3.4 设备侧约定（建议写进协议）

- 同一设备同一时刻只允许一个进行中的会议；重复 `start` 用同一 `client_key` 返回原会议。
- 本地录音缓存：建议至少缓存最近 5 分钟，断网不丢；上限由设备存储决定。
- 上传失败：指数退避（如 1s / 2s / 4s / 8s，最多 5 次），仍失败则本地保留并在下次联网补传。
- 结束前必须把本地缓存全部分片尝试上传；`end` 返回缺片后按列表补传。
- 设备屏幕只显示「录音中 / 上传中 / 已完成 / 失败」，不显示转写文本（与现有产品口径一致）。
- 开始录音必须有本地提示（提示音 / 指示灯 / 屏幕），且只能由现场按键触发；**不提供远程静默开启接口**。

### 3.5 需要端云确认的选项

1. 会议走 HTTP 还是 WSS：**建议 HTTP**（30 秒分片、无需长连接、断网续传简单）。
2. 分片 30 秒还是 60 秒：建议 30 秒（单片约 960KB，2MB 上限内）。
3. `sha256` 是否必填：建议必填，便于定位坏片。
4. 本地缓存时长：建议 ≥5 分钟，具体看设备存储。
5. 设备是否需要显示「转写中 / 纪要已生成」：建议只显示状态，纪要留在后台。
6. 取消会议是否删除已上传音频：需产品与合规确认。
7. 现场提示话术与触发方式：需业务确认（已登记在《开发待确认问题清单》第 9 条）。

## 4. OTA 协议：要不要改

### 4.1 结论

**OTA 协议本身不需要改。** 会议录音只是「新固件」，继续走现有 `check → 签名下载 → 安装` 即可。

### 4.2 需要补的是「版本与功能开关」

| 需求 | 建议做法 |
|---|---|
| 云端知道设备是否支持会议录音 | `session_init` 增加可选 `features`（如 `["meeting_recording"]`）；`config_update` 增加 `features` |
| 云端知道设备固件是否够新 | 设备上报 `fw_version`；云端按最低版本拦截会议接口 |
| 设备知道云端是否开启会议功能 | `config_update.meeting.enabled` + `chunk_sec` / `retention_days` |
| OTA 强制升级 | 现有 `policy: mandatory` 已支持；会议功能可要求最低版本 |
| 灰度发布 | 现有 OTA 文档已预留灰度分组；按门店 / 群组放量 |
| 回滚 | 设备回滚后 `features` 不再上报，云端自动关闭会议入口 |

建议的兼容规则：

- `session_init.features`、`config_update.features` 都是**可选、向后兼容**；旧固件不传，云端按「不支持」处理。
- 会议接口在云端做双重校验：`features` 包含 `meeting_recording` + `fw_version ≥ 最低版本`。
- OTA `check` 响应不新增字段，避免把功能开关塞进 OTA 协议；OTA 只负责发固件。

> 已确认：`application.yml` 中 `spring.jackson.deserialization.fail-on-unknown-properties: false`，旧固件不认识的字段会被忽略，新增 `features` 向后兼容。

### 4.3 OTA 实现与冻结稿的差异（需确认）

| 项 | 冻结稿要求 | 当前实现 | 影响 |
|---|---|---|---|
| 固定配套 | 云端维护「起始组合 → 中间组合 → 目标组合」迁移表 | 只按唯一 active release 的目标版本，返回尚未达标的包 | 若端侧存在「必须先升中间版本」的芯片，当前会直接给目标包，需补迁移表 |
| 灰度 | 字段预留、默认全量 | 一致 | — |
| 结果感知 | 下次 check 被动感知 | 一致 | — |
| 错误格式 | `{error_code, message}` | `OtaExceptionHandler` 输出同格式 | 一致 |
| 鉴权 | Bearer device token | 一致 | — |

> 中间组合是 OTA 唯一需要端云再确认的实现差异；如果 1.0 的 P4/C5 不存在跨版本依赖，可以先接受当前实现，并在文档中写明「1.0 不做中间组合」。

## 5. 其他场景的协议影响

| 场景 | 当前协议 | 需要补什么 | 影响 |
|---|---|---|---|
| 运营通知已读 | 复用 `broadcast` + `broadcast_ack`，只有投递 | `notice` / `notice_ack`，或给 `broadcast` 加 `requires_ack` / `notice_type` | WSS v1.1 增量 |
| 会议待办提醒 | 无 | `action_reminder` + `action_ack`，或复用 `notice` | WSS v1.1 增量 |
| 报表推送 | 无 | `report_ready` + `report_ack`（只通知，不传报表内容） | WSS v1.1 增量 |
| 维修 / 点检任务 | 无 | `task_assign` + `task_ack` + `task_result`；或设备走 HTTP | 需单独设计，建议放 v2 |
| 知识缺口反馈 | 无 | 复用 `notice` 通知门店 / 提问人 | 增量，不新增类型 |
| 配置 | `config_update` | 增加 `meeting`、`notice`、`features` | 兼容增量 |
| 设备状态 | `session_init` 有网络 / 耳机 | 增加电量、存储、录音状态 | 兼容增量 |
| OTA | 已冻结 | 只补最低版本 / 功能开关说明 | 不改接口 |

> 原则：**能复用 `notice` 的不要新增消息类型**；只有维修 / 点检这种「派任务 + 回填结果」的交互，才值得单独设计一套消息。

## 6. 版本与治理建议

### 6.1 把三个版本分开

| 版本 | 含义 | 当前 |
|---|---|---|
| **协议版本**（`proto_ver`） | 帧结构 / 消息语义是否兼容 | 1 |
| **文档修订** | 规范文档改到第几版 | 文件名 v1，内容 v4/v5 |
| **设备 HTTP API 版本** | `/api/v1/...` 路径 | OTA 有 v1；会议没有 |

建议：

- `proto_ver` 只表示大版本；新增 `proto_minor`（可选）或 `features` 表示能力。
- 规范文档标题改为「WSS 会话协议 v1 · 文档修订 v5」，文件名不再承担版本号。
- 设备 HTTP 接口统一 `/api/v1`；后台内部接口保持 `/api`。

### 6.2 鉴权统一

| 通道 | 现状 | 建议 |
|---|---|---|
| WSS | query `device_id` / `token` | 保持（ESP32 WebSocket 方便）；文档注明例外 |
| OTA | `Authorization: Bearer` | 保持 |
| 会议 | `X-Device-Id` + `X-Device-Token` | 改为 `Authorization: Bearer` + `X-Device-Id`，与 OTA 一致 |

### 6.3 错误格式统一

- HTTP：`{ error_code, message, retryable }`
- WSS：`{ type:"error", code, message, fallback_action }`
- 两套可以不同，但都要有稳定错误码表，设备按码处理，不解析文案。

### 6.4 变更流程

1. 提出变更（端侧 / 云端 / 产品）
2. 填影响矩阵：影响哪些消息、哪些固件版本、是否向后兼容
3. 端云双方确认
4. 更新规范 + 变更记录 + 测试用例
5. 冻结并发布

建议在 `docs/` 下建立协议索引，至少包含：权威文档、当前版本、冻结日期、负责人、变更记录。

## 7. 对齐会需要拍板的事项

| # | 事项 | 建议 |
|---|---|---|
| 1 | 会议录音走 HTTP 还是 WSS | **HTTP**（分片上传，不依赖长连接） |
| 2 | 分片 30 秒还是 60 秒 | **30 秒** |
| 3 | `last_seq` 是否必填 | **必填**，否则末尾丢片发现不了 |
| 4 | `end` 是否返回缺片列表 | **返回 `missing_seqs`** |
| 5 | 是否增加状态 / 续传接口 | **增加 `GET /meetings/{id}`** |
| 6 | 音频格式是否只支持 PCM16 | **v1 只支持 PCM16**；Opus 后续 |
| 7 | HTTP 鉴权是否统一 Bearer | **统一**，与 OTA 一致 |
| 8 | 是否增加 `features` / 功能开关 | **增加**，放 `session_init` 和 `config_update` |
| 9 | 会议最低固件版本 | 端侧给出首个支持版本后冻结 |
| 10 | 现场提示话术 / 触发 | 产品 / 业务确认（已登记待确认清单） |
| 11 | 取消会议是否删除音频 | 产品 / 合规确认 |
| 12 | 通知 / 待办 / 报表的已读回执 | 先做 `notice` + `notice_ack`，复用一套 |

## 8. 下一步

1. **云端**：把《会议录音 HTTP 接口 v1》写成正式协议文档（含状态机、错误码、限制、续传）。
2. **云端**：补 `missing_seqs`、`GET status`、`abort`、统一鉴权与错误信封。
3. **云端**：在 `session_init` / `config_update` 增加 `features` 与 `meeting` 配置；确认旧固件兼容。
4. **端侧**：确认长按开始 / 结束、本地缓存、重试策略、现场提示方式。
5. **双方**：开一次协议对齐会，逐条过 §7 的 12 项，拍板后冻结 v1.0。
6. **测试**：幂等、重复上传、缺片补传、重启续传、鉴权失败、分片超限、过期、弱网、OTA 升级后功能开关。
7. **文档**：更新协议索引、联调说明、OTA 文档中的「最低版本 / 功能开关」说明。

> 建议先不改已冻结的 WSS v1 与 OTA 协议，只做**增量、可选、向后兼容**的扩展；会议录音单独成文、单独版本化。
