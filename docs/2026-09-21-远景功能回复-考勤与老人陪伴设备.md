# 关于《远景功能落地方案补充整理》的两点回复

> 致：测试、需求同事
> 日期：2026-09-21
> 范围：针对《远景功能落地方案补充整理.docx》**第 6 条（劳务派遣考勤）**、**第 8 条（介护老人陪伴设备）** 的结论回复

---

## 一、劳务派遣「考勤」——采纳，但 1.0 只做「到岗登记」

### 你们的建议（要点回顾）

考勤入口需重新定义：员工如何打卡、是否要定位、是否要防代打卡、项目切换、休息/加班、考勤数据去向、是否对接考勤系统等。

### 结论：建议成立，采纳；但 1.0 范围收缩为「到岗登记」

同意「考勤入口需要重新设计」的判断。但其中「**定位、防代打卡**」这两项，1.0 **不做**，原因如下：

**定位 + 防代打卡 = 纯监控（防人），与产品定位冲突。**

我们的产品定位是「帮一线把事做成的 agent，**不是监控员工的工具**」（这是近期已对齐的核心口径）。定位追踪、防代打卡本质是「证明员工没偷懒 / 没代打卡」，属于「防人」而非「成事」。一旦做进 1.0，会：

1. 引发一线员工与中层（店长 / 班组长）的抵触，导致「阳奉阴违」——员工把聪明用在躲检查上，而不是把事做好；
2. 与日本 APPI 下「位置信息」等敏感数据叠加，合规成本陡增；
3. 稀释 1.0 的核心价值焦点。

### 1.0 怎么做（最小范围）

考勤在 1.0 只做「**到岗 / 离岗登记**」这一个动作，且**尽量复用现有交互，不新增硬件、不新增定位**：

- 员工通过工牌按键（方向键 + 确认键菜单，或语音）做一次「到岗确认」；
- 到岗登记作为「主动提醒 → 执行 → 回执」闭环的**副产品**：例如派工 / 任务下发后，员工确认收到 / 完成即自动记为到岗；
- 数据回流到后台看板（到岗率、出勤统计），供管理者「**看清一线**」而非「**盯住一线**」。

### 延后到 2.0 单独评估

定位、防代打卡、考勤系统对接、复杂规则（项目切换 / 休息 / 加班 / 工时合规）——这些涉及合规与「防人」权衡，留到 1.0 稳定后单独立项评估。

---

## 二、介护「老人陪伴设备」——单独立项，1.0 不混入

### 你们的建议（要点回顾）

介护场景可从「员工工具」扩展到「老人本人使用」：主动提醒（吃药 / 康复）、AI 陪伴、呼叫介护人员，形成「老人 → 设备 → 介护人员」链路。你们也指出这已不是 B2B 员工工牌，而是 **B2B2C 养老 AI 终端**，需单独做定位 / 权限 / 隐私 / 紧急呼叫 / 数据保存设计。

### 结论：方向认可，单独立项；1.0 不混入

这个方向（老龄化 + 陪伴 + 主动提醒）是**真实且有价值的赛道，判断成立**。但正如你们自己指出的，它已经**不是「员工工牌」这个产品**，而是「B2B2C 养老 AI 终端」。

决策：

1. **1.0 不混入**——避免稀释工牌的产品焦点，也避免「要配虑个人情报」（老人病史 / 健康数据）的合规复杂度拖累 1.0 交付节奏。
2. **记录为独立产品方向（Backlog）**——待 1.0 工牌稳定后，单独做：产品定位、目标用户、权限模型、隐私与数据保存、紧急呼叫、设备形态等设计。
3. **1.0 仍保留介护的「员工侧」价值**——工牌给**介护员**用（不是给老人用）：照护知识库、定时翻身 / 服药提醒（提醒对象是介护员）、护理日志、呼叫支援（介护员 → 组长）。

### 建议给到需求的要点

- 介护场景 1.0 需求边界：明确「工牌的使用者是**介护员**」，老人陪伴相关能力**不进 1.0 需求清单**。
- 「老人陪伴设备」作为独立方向单列，待立项后再展开。
